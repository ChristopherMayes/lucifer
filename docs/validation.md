# Validation: what is checked, how, and at what measured level

Lucifer's physics is transcribed from Genesis 1.3 Version 4 (Genesis4) and validated against it from bitwise-identical starting states. This page is the measured record: the rule every commit obeys, the tier table with its recorded digits, the check sections that run on every validation pass, and what each measurement pins, subsystem by subsystem.

The physics itself is the manual, [`fel-physics.md`](fel-physics.md): every equation the code integrates, each subsystem's Genesis4 provenance, and which check pins it. This page carries the numbers. Where a section here touches physics it links to the manual section.

(val-what-is-tested)=
## What is tested, and where

The keystone is the run every commit passes before it lands. It runs five jobs at once: the validation suite on the debug build and again on the release build, Bmad's own regression suite, the wavefront validation and the examples. Each job must pass its tolerances. The keystone then regenerates the generated pages and requires them to equal the committed ones, so a recorded digit that moves fails it. A commit that means to change a generated page, with a new check row or a changed file layout, reviews and commits the page, and the next keystone must reproduce it exactly. `tests/test_keystone.py` runs it, and [](#val-the-keystone-rule) gives the commands.

The validation suite is `tests/run_fel_validation.sh` with its check scripts. It holds the Genesis4 tiers and the check sections below. The Linux CI job runs it too, at its tolerances, and is not a keystone.

| Test | Compares against | Build | Runs in | Judges |
|---|---|---|---|---|
| The Genesis4 tiers, in the validation suite | Genesis4 4.6.15, both codes started from the same dumps | debug and release in the keystone, debug in CI | the keystone and the Linux CI job | each tier's largest relative difference against its tolerance |
| The check sections, in the validation suite | identities, closed forms, independent routes to one number, invariance under a change that must not matter, and refusals | debug and release in the keystone, debug in CI | the keystone and the Linux CI job | each check's measured value against its stated bound |
| The recorded digits | the committed generated pages: the tables in `docs/generated/validation-measured.md` and the example pages written from `examples/measured.tsv` | debug and release | the keystone alone | that the regenerated pages equal the committed ones |
| Bmad's regression suite | Bmad's own `output.correct` files | Bmad's debug binaries | the keystone alone | the Bmad build Lucifer links against |
| The wavefront validation, `tests/wavefront/run_validation.sh` | openPMD-beamphysics and an in-Fortran reference propagator | debug | the keystone and the Linux CI job | the largest relative difference against its tolerance |
| The examples, `examples/run_examples.sh` | the bank bytes each run's header states | release in the keystone, debug in CI | the keystone, and in CI steady_state alone from the installed tracker | that each example runs and writes its record, with the notebook, link and retired-word checks |
| The performance benchmark, `tests/run_perf_benchmark.sh` | Genesis4's wall clock on the same line, and the tracker's own phases | release | an idle machine, by hand | wall clocks, recorded with their toolchain and day in [`performance.md`](performance.md) |

No test in the keystone or in the Linux CI job judges a wall clock. The validation suite prints each section's time as the cost of the check, and nothing reads it. Each keystone job has a one-hour timeout, which stops a hung run. The performance benchmark is the one timing measurement, and it runs on an otherwise idle machine because a shared CI runner gives clocks that do not repeat.

The Linux CI job builds the debug configuration on purpose. `-fbounds-check` turns an out-of-bounds read into a failure instead of a wrong number. Five wake cases once failed on Linux by reading past the end of a one-element vector, which the macOS allocator had answered with a number that happened to work. The CI job asserts tolerances and not the recorded digits, since a different FFTW and HDF5 change the last digits by construction ([](#val-second-toolchain)). A release build is validated on the recording machine alone.

(val-the-keystone-rule)=
## The keystone rule

Every commit is validated before it lands, and the tiers land on their recorded digits. A moved digit is a bug and not a new baseline. The generated [HDF5 file layouts](generated/layouts.md) page is held to the same diff under a different rule. A moved line there is a change to the files this program writes, to explain, review, regenerate and stage. It is neither a bug nor proof that a schema changed, since the regeneration shows only that the page agrees with the output and cannot show that the change was reviewed. The keystone runs from the root of the Lucifer repository, with `BMAD_DIR` naming a Bmad checkout and the interpreter of the `bmad-fel-validate` environment:

```
BUILD_PRODUCTION=N util/conda_compile      # debug: Bmad, then Lucifer
util/conda_compile                         # production
python3 -m pytest tests/test_keystone.py -v
```

The build script builds the Bmad distribution and then Lucifer against it with Lucifer's own CMake, into `build-debug/` and `build-release/` at the repository root ([building](user-guide.md#building)). The keystone stays on that distribution build, and not on the conda-forge `bmad` package the user guide gives first, because the package is a production build of Bmad: the debug pass runs Bmad bounds-checked as well as Lucifer, and the regression job reads Bmad's suite and its debug binaries from the checkout, and the package carries neither. A Lucifer built against the package runs the validation suite at its tolerances, which is what the Linux CI job does. The Bmad release is a minimum, declared in `BMAD_RELEASE`. The build script and the suite's preflight both run `util/bmad_release_check` against the checkout, and the preflight runs its self-test first. The Linux CI job installs the conda-forge `bmad` package from `environment.yml`, runs the same check on the package's prefix, and builds Lucifer against it. A green run there certifies that release and no later one. The suite takes four locations: the Lucifer source, which is its own tree, the Bmad source with its regression suite and debug binaries (`BMAD_DIR`, else `DIST_BASE_DIR`, else the Lucifer source's parent), and the two Lucifer binary directories (`LUCIFER_DEBUG_BIN`, `LUCIFER_PRODUCTION_BIN`), which default to `build-debug/bin` and `build-release/bin`. openPMD-beamphysics is a package in the validation environment, 0.16.3 or later, and *not* a location. A relative value is taken against the directory the suite was started in. Every job is handed the resolved absolute values, since the jobs run from the Lucifer source. A `BMAD_DIR` naming a directory with no `util/dist_source_me` is passed over with a note, since `dist_source_me` uses that name as a loop variable and leaves it at the checkout's `util/` once sourced. The shell scripts take the same rule from `util/locations.sh`, which they source.

The suite launches the five jobs at once, each from an absolute working directory into its own log under a fresh artifact directory it names, and keeps every outcome, a launch that failed and a job that timed out included. Five tests read those outcomes, one each. A sixth regenerates the seven page sets and requires the diff to be empty: the validation tables, the Fortran and the Python references, the schema with its models and key tables, the example pages, the startup-noise tables and the layouts. It verifies for itself that all five passed before it runs a generator, so it cannot pass on a partial run and does not lean on test order. Selecting one test still runs all five jobs, xdist is refused, and a job past its hour is killed as a process group. The five jobs are the ones below, unchanged. The suite launches them from fixed directories, where a retyped recipe can launch the validation suite from a directory an earlier command moved into and report a complete keystone from a partial run.

```
./tests/run_fel_validation.sh --exe $PWD/build-debug/bin/lucifer --build debug \
        --results <art>/fel-debug.txt --work-dir <art>/wd-dbg
./tests/run_fel_validation.sh --exe $PWD/build-release/bin/lucifer --build production \
        --results <art>/fel-prod.txt --work-dir <art>/wd-prd
(cd $BMAD_DIR/regression_tests && pytest test_fortran.py --bmad-bin=$BMAD_DIR/debug/bin)
./tests/wavefront/run_validation.sh
./examples/run_examples.sh --no-figures
```

The five run at once because they share only a source tree they read: separate work directories, separate output roots, and no shared state anywhere else. Nothing persists FFTW wisdom or writes outside its own directory. On an M3 Max the whole thing takes 7.7 minutes with the Genesis references cached and 9.2 without, against 25 minutes with every step in sequence and the references regenerated twice per run. The references are cached because they are a pure function of the reference binary and the input files that make them. The cache key names both and the pinned version besides, and each run says whether it hit or missed. Deleting `~/.cache/lucifer/genesis-refs` is always safe and costs one cold run.

| step | cached | cold |
|---|---|---|
| both validation passes, regression, wavefront and examples, concurrent | 458 s | 551 s |
| the regeneration below | 2 s | 2 s |
| total | 7.7 min | 9.2 min |
| the same work in sequence, before this arrangement | 25 min | 25 min |

Those are the shell recipe's measurements. The pytest suite's first three runs on the same machine took 11.2 to 11.6 minutes. That is a separate observation. The cache state, the machine's load and the check sections were not matched between the two recipes, and the difference is not attributed to anything until they are.

The examples job runs its directories a few at a time. A directory is the unit and never an input file, because the import example's second input file reads the openPMD file its first input file writes. Directories share only the lattice files they read. Every input file's return code, elapsed time and exit line are collected in the worker that ran it. The table is printed after every worker has finished, in the order a one-worker run prints it. An input file that left no outcome at all is printed and fails the job, which is the case a schedule that silently skipped a directory would otherwise pass.

The examples job was measured alone on an M3 Max of 12 performance cores, with no other keystone job running:

| workers | 1 | 2 | 3 | 4 | 6 |
|---|---|---|---|---|---|
| seconds | 390 | 293 | 262 | 255 | 248 |
| peak resident memory (GB) | 0.5 | 0.7 | 0.9 | 1.3 | 1.6 |

The default is one worker per four performance cores, at most three, which is three on that machine. One example run is already parallel and draws 8.4 cores on average and 11.7 at its peak, so the fourth worker finds little idle capacity and buys 7 seconds. Every input file ran on the twelve threads the OpenMP runtime chose for it, which the run header prints and the runner does not set. That count is the same at every worker count. The directory, input file, exit status and exit line columns were identical across every schedule from one worker to six, the sequential run included.

Inside a keystone the examples job takes two workers, which the suite passes to it. While the validation suite's check sections ran in sequence the examples were not on the critical path, and capacity they took came from the two validation passes that were. At three workers the examples job finished in 347 s against 570 s at one. Every other job slowed, two runs at each setting. The debug pass went from 694 s to 748 s, the production pass from 472 s to 542 s, the regression suite from 155 s to 245 s and the keystone from 11.6 to 12.5 minutes. With the check sections concurrent the passes finish sooner. At one worker the examples job then finished last, 592 s of a 592 s keystone. At two workers the keystone took 573 s and the debug pass finished last, and the two runs that followed took 579 s and 575 s.

The validation suite's check sections run several at once after the tiers. Each section runs in its own directory under the work directory, with the lattices and reference input files it may read copied in. The source-filter section alone also takes the converted reference it compares against. Nothing a section writes is read by another. The two sections that read the tiers' outputs, thread-independence and tier-comparison, keep their places. The output is printed after every section has finished, in the order the script lists them, each with its own wall time. A results row is written for a pass or a skip and never for a failure, so a results file with a section missing names the section that did not pass. A section that left no record did not run, and that fails the pass too.

Each check a section's script makes is recorded as well as judged. Beside the line it prints, the script calls `checkrec.record` with the check's name, the value it measured, the bound it held the value to, the sense of the comparison and its verdict. The validation suite names the file each section records into, and after the section passes it appends those lines to the results file beside the section's outcome, each as `check|` followed by the record as JSON. `report_validation.py` pairs the two builds' records by section and by name and writes one table per section into the generated page, so the measured levels below are written by the scripts that measured them. It refuses a name recorded twice in one build and a check recorded in one build and not the other. A script run by hand, with no record file named, writes no record and behaves as it did.

The cores a pass may spend are one allocation, `--cpus`, and the sections of a pass spend it once between them. A check run takes four threads, so the allocation over four is the number of sections run at once. Each section hands the allocation over that count to the pools inside its check script through `LUCIFER_CPU_BUDGET` (`tests/scripts/pool.py`). A pass run by hand takes the performance cores. In a keystone the suite hands each pass the full count, the examples two workers, and the regression suite and the wavefront validation one process each. That is above the core count at its widest and is a measured choice. The device is one resource across both passes, so their device sections take turns under one lock (`tests/scripts/with_lock.py`) while the CPU sections of either pass carry on beside them. The wait is printed. The debug pass waited 17 to 24 s for the production pass's device section on each of four concurrent keystones.

Three keystones before and three after were measured on the same M3 Max, at matched cache state with the machine otherwise idle:

| | before, sections in sequence | after, three sections at once a pass |
|---|---|---|
| keystone wall time (s) | 696, 690, 689 | 573, 579, 575 |
| debug pass (s) | 696, 690, 689 | 572, 578, 575 |
| examples job (s) | 568, 566, 562 | 461, 458, 453 |

Ordering the tier blocks, below, took the keystone to 523 to 529 s.

The wall times are the comparison. Utilization and memory are supporting observations with one baseline sample, since the sampler failed silently on two of the three baseline runs. The one sampled baseline averaged 978% CPU of the machine's 1600% over the run, and the three concurrent runs averaged 1210%, 1218% and 1217%. Peak resident memory summed over every tracker, reference and check process was 4.3 GB on the sampled baseline and on each of the three concurrent runs.

The debug pass alone, with no other job running, took 365 s against 692 s under the old schedule inside a keystone, and its concurrent phase took 233 s.

With both passes reaching their tier blocks at the same moment, eleven single-thread processes each is twenty-two on twelve cores. The block then took 216 to 225 s inside a keystone against 115 s alone. The suite lets the debug pass, which finishes last, through the block first and holds the production pass at its own block until a marker says the first is done (`--tiers-marker` and `--wait-tiers`). The held pass runs its setup meanwhile. The wait is bounded at 900 s and says which way it went, so a pass whose partner died before writing the marker runs its tiers rather than waiting out the keystone. Over three keystones the keystone took 523, 525 and 529 s against 573, 579 and 575 s with the blocks overlapping. The debug block took 168 to 172 s. The production pass waited 169 to 173 s and then took 134 s of its own, and the two passes finished within 5 s of each other. Mean CPU rose from 1210 to 1218% to 1278 to 1319% of 1600%. Peak resident memory fell from 4.3 GB to 3.4 to 3.5 GB, since eleven trackers hold the machine at that moment rather than twenty-two.

Widening one section's allowance was measured and rejected. The spontaneous section ends the debug pass's concurrent phase, and its check script's pool, sized from the four cores a section is given, ran its thirteen-run scan one at a time. With half the pass's cores the section fell from 326 s to 230 to 245 s, and the keystone rose to 626, 637 and 640 s. A section holding half the allocation leaves room for one other beside it rather than two, and mean CPU fell to 1067 to 1121%. The pass was already spending its allocation: its sections reserved 3984 core-seconds of the 3996 a 333 s phase at twelve cores can hold. Moving cores between them buys nothing and costs the parallelism it takes away. Equal shares stand, and the phase is 328 to 337 s.

The critical path is the debug pass, at 523 to 529 s of a 523 to 529 s keystone, and inside it the concurrent phase, which the spontaneous section at 318 s still ends. The device lock costs 44 to 49 s of waiting in one pass or the other, inside a phase that ends later than the wait does.

Every section runs in every keystone. Nothing is behind a flag, and there is no shorter mode. A cheap run that checks less is what a keystone exists to prevent.

Then regenerate the documentation that is generated, and require no diff. Both halves are the check. The diff alone asks only whether someone hand-edited a generated file, and a page that no longer describes the code passes it. The five commands are one step, which the suite's regeneration test runs.

Regenerate then diff checks that the committed generated pages agree with what the current sources generate. It does not detect a page hand-edited in the working tree: the regeneration overwrites the edit, and the diff then compares the regenerated page with the committed one, which agree. The keystone removes such an edit and leaves the tree consistent. What the step does catch is a committed page whose source has moved, or a source that changed without its page being regenerated and committed. A word moved in a routine header fails the diff, which prints the page.

The Linux CI job (`.github/workflows/lucifer-linux.yml`) is a different check, and a green run of it is not a completed keystone. The CI job builds Lucifer's Debug configuration against the conda-forge `bmad` package, a production build of Bmad with no regression suite, and asserts the validation suite's tolerances rather than the recorded digits, which belong to the machine that recorded them. The CI job establishes portability and physics agreement within tolerance under that build configuration. The keystone establishes both builds, all five jobs, the regeneration and agreement with the recorded results, and only the suite above does that. Widening the CI job to the full suite would need a decision about platform-specific numerical expectations, and that decision has not been taken.

```
python3 tests/scripts/report_validation.py \

python3 tests/scripts/report_api.py \
        --code src --code programs --out docs/generated/api.md
python3 tests/scripts/report_python_api.py --out docs/generated/python-api.md

git diff --exit-code -- 'docs/generated/*.md' 'python/lucifer/schema.json' 'python/lucifer/models.py' 'docs/generated/examples/*.md'
```

The startup-noise generator writes the measured tables of [](startup-noise.md) from the JSON that `tests/scripts/startup_noise.py` commits beside its figures, one file per machine, and the page includes each table from the generated file. The driver runs on demand and never in the keystone, so the regeneration renders the committed record at no run cost, and the page's provenance table says which commit, build, backend and day measured it.

The layouts generator runs four small input files with the executable it is handed, in a scratch directory of its own. It prints the hierarchy of eight of the files they wrote: every group, dataset, link and attribute, with no dataset values, and the values of two attributes left out by name, `date` and `softwareVersion`. It writes the page whole after every fixture ran. A failed fixture therefore fails the regeneration test, keeps its log beside the jobs' logs, and leaves the committed page as it was. The independent view of the same files is HDF5's own tool, which shows what the printer does and the values besides:

```
h5dump -H run-000005.beam.h5           # the hierarchy, datatypes and attributes, no data
h5dump -a /lucifer/checkpoint/checkpointFormat run-final.beam.h5
```

The page covers the files the writers produce. The files a check forges to provoke a refusal, a stripped residual or a missing checkpoint member among them, are the check's own and are not printed.

The measured levels in this document are written by the validation suite that measured them, so a moved digit is a failing command rather than a discrepancy someone has to notice while reading. The validation suite's `examples` section generates the example pages into its own directory and compares them with the committed ones, so a stale committed page fails that section. The regeneration above is the one write into the tree.

The diff names the Markdown. The figures in `docs/generated/examples/` are committed beside the pages and deliberately excluded. A plotting-library upgrade rewrites every one of them byte for byte without changing any physics, and a check that fails on that is a check that gets switched off. `examples/run_examples.sh` writes them, and the examples check asserts that each page's figure exists rather than what it contains.

The regression suite reports 54 passed and 3 skipped. Build in the `bmad-build` environment. The validation suite runs its Python in `bmad-fel-validate`, which also carries the `genesis4` the comparison runs against, from conda-forge and pinned in `tests/environment-validate.yml`. The validation suite takes that one rather than searching PATH, because the levels recorded here belong to the build that produced them. `--genesis <path>` or `$GENESIS4` names a different one, which the version check then has to accept. It refuses whatever does not report the recorded version, however it was named.

The levels here were measured against the Genesis4 4.6.15 release. The validation suite refuses a reference reporting any other version rather than running against it, printing the one it found and the one it wants. The failure it prevents is silent: a different reference moves the recorded digits while every tolerance still passes. Two properties of 4.6.15 are load-bearing. It carries the CODATA electron rest energy, which is also Bmad's `m_electron`. Releases to v4.6.14 carried a value 2.14e-7 above it and loosened the transcription tiers by several percent of their own value ([](genesis4.md) states the constant and the size). And it seeds each stochastic stream from the global slice index, which this project contributed upstream, so noise realizations differ from every earlier release. The digits below were re-recorded on that migration, and which of them moved is stated in the changelog with the reason. The regeneration check refuses to absorb a reference change either way: it shows up as a non-empty diff on the generated table rather than as quietly different digits. Only environments this project created are used. An unrelated `devel` environment on PATH once caused an HDF5 mismatch, and the same class of mistake is why the reference's own variant is chosen to match the HDF5 its environment already runs.

Debug and production binaries are never bit-comparable to each other. Compare like builds only.

(val-second-toolchain)=
### The same checks on a second toolchain

Every level in this document was measured on one machine, an M3 Max running macOS, with one toolchain, gfortran 15.3 and clang 21.1 from conda-forge, since a digit depends on the compiler as it depends on the machine. A second platform finds a class of defect the first one hides. Five wake cases once failed on Linux because a steady-state run read past the end of a one-element vector, and the macOS allocator had been answering with a number that happened to work. `.github/workflows/lucifer-linux.yml` builds the debug tree on Linux and runs the validation suite and the wavefront validation there. The debug build is the point, since `-fbounds-check` turns that read into a failure rather than a wrong number.

That build is a conda build, for the same reason the recording machine uses one. Bmad ships on conda-forge, so a conda build is the configuration most users run, and a check against what is delivered reaches more than a check against a configuration only the off-site distribution assembles. `util/conda_compile` automates it here and the workflow writes the same preferences there, so the CI build and the recorded levels come from one arrangement.

That run asserts the tolerances and not the digits. A different FFTW and HDF5 give different last digits by construction, so the levels recorded here stay a property of the machine that recorded them. On its first run all eleven tiers passed, four of them on digits identical to the ones above and seven moved in their last places. It takes 37.5 minutes on a four-core runner, of which the validation suite is 30. It runs on every push to the default branch, on demand and weekly, and a later push cancels a run in progress. Bmad's own `ci.yml` builds the whole distribution on every push to Bmad.

The device section is the one section allowed to skip, and it skips there with its reason printed and recorded: a Linux build carries the refusing stub, so it has no backend to judge. The skip keys on what `lucifer` answers when run with no arguments, which names the backend the build carries and the machine under it, so a machine with a usable backend cannot skip. A results file recording that skip cannot write the generated table, which `report_validation.py` refuses. That table lists every section that ran, and a run one section short would undercount them.

(val-crossidentities-not-reference-files)=
## Cross-identities, not reference files

Almost nothing here is checked against a stored expected-output file. A reference file records what the code did once. An identity records what must be true of any correct implementation, and it stays valid when the code is rewritten underneath it. So the checks are conservation laws, closed forms, independent routes to the same number, invariance under a change that must not matter (thread count, weight splitting, a no-op), and refusals that state what they reject.

A check that has never failed on a real defect is untested, so several here carry their own mutation record: what was broken deliberately, and how loudly the check noticed. A measurement without a stated tolerance is not a check, so every number below is paired with the level it is held at.

(val-the-transverse-grid)=
## The transverse grid, and where the reference cannot be followed

Every input file the validation suite runs carries a power-of-two transverse grid, and the derived count rounds up to one ([](input-reference.md#param-wavefront-grid)), so an input file runs on the CPU and on the Metal field solver unchanged. The LCLS example shows what that buys: 300 slices of 4096 macroparticles at grid 128, one input file, and the two backends land at 7.407 TW against 7.404 TW on exit power and 253.674 uJ against 253.561 uJ on pulse energy. That is a relative 4.1e-4 and 4.5e-4, inside the device's own 5.1e-4 band. Before the grids moved the same input file derived 127 points on the CPU and 128 on the device, so no such comparison could be made at all.

Those grids are what made a defect in the field solver's propagator reachable. The transverse wavenumbers were built as an offset index, which lands on whole multiples of the fundamental only when the point count is odd. On an even count every mode was propagated half a step out and the constant mode at half a step rather than at zero, and the error grows with the mode. The kernel now builds the wavenumbers the transform carries. On an odd grid the two tables are the same one, so the change is bit-identical there and every digit recorded on an odd grid is unmoved, checked by building both and running one input file in one directory. On an even grid it is a correction of 1.4e-1 peak normalized on the 57 m line at 256 points.

Genesis4 builds the same table the same way, so this was transcribed faithfully and the defect is upstream. The two codes therefore agreed with each other on an even grid, at 1.4e-6, while both were wrong, and no comparison against the reference could find it. The one tier that compares two models of the same thing inside this code found it, the Bmad seam against the transcribed interlude, since the seam moves the field with `wavefront_drift`, whose wavenumbers were right at both parities.

Four places therefore hold an odd grid on purpose, each saying so where it is written. The five Genesis reference input files under `tests/genesis4/` and the harmonic and phasing checks compare against Genesis at levels between 1e-6 and 1e-3, and a comparison that tight has to run where the reference is right. At 64 and 256 the harmonic tier reads 1.4e-3 against a 1e-6 level and the phasing curve 1.0e-6 against the same. The saturation demo is held for the same reason. And `lucifer_smoke_test` with its namelist twin stays at 63 to keep the odd-grid path itself under test, since a user may write an odd count and an imported Genesis field can carry one. The device refuses an odd grid and names the nearest supported size, which `check_device` asserts. Those exceptions go away when the upstream fix lands.

The other four checks that run Genesis4 are unaffected and stay on powers of two. The distribution import, the SASE startup cross-check, the beam format check and the device's own Genesis comparison compare loaders, formats and short propagations rather than a long field solve. The device's Genesis anchor at grid 64 moved with the correction, which is the upstream defect measured on a short planar segment, and its level sits well inside that check's bound ([](#val-levels-device)).

A power-of-two grid has a parity cost of its own, apart from the reference. On an even count the axis falls between four cells. A beam on the axis then reads a centred field low by the cell squared over twice the waist squared through the bilinear gather, and the deposit returns the same deficit. An odd count puts a cell on the axis. `check_diagnostics.py` measures that cost on the steady-state example's input file, at its 256 points and at 255 with the cell held, as the exit power's relative difference, and the row is in [](#val-levels-diagnostics). The checks whose reference is an analytic value of a field the beam samples on the grid were each run at both parities of one cell. The unaveraged coupling probes moved by half their tolerance and run on an odd grid for it ([](#val-the-unaveraged-mode-fc)). The in-cone startup moved by a tenth of its tolerance. Its target comes from the startup-noise page's input file on the same 256 points, which today's binary reproduces. The seed containment, the spontaneous capture, the coherent source's limit identity and the harmonic one-step deposit moved by far less. The numbers are in the changelog.

(val-validation-from-one-command)=
## Validation, from one command

The validation suite runs Genesis4 six times (full line and single segment, steady state and time dependent, plus the collective tiers). It converts each chain's initial dumps to openPMD, which is the only format the tracker reads, runs the Bmad tracker for every tier and check, and prints the largest relative difference of each check. It fails if the genesis4 binary is missing, and likewise without openPMD-beamphysics installed in the validation environment, which performs the conversion. There is no comparison without either, so there is nothing to skip to. Genesis4 must be built with FFTW, since the validation suite runs with `fft_fieldsolver=true`. The Bmad tracker transcribes the FFT solver, and Genesis4's default ADI solver is out of scope.

Both codes start from the same Genesis4 `&write` dumps, so the initial state is bitwise identical and no loader is reproduced. Genesis4 records diagnostics once at the start and once per integration step, with each interlude element being a single step. The tracker records at the same z positions (per slice, in time-window order, for the time-dependent tiers). The measured levels are:

That panel shows what a phase-dominated tier number is made of. For `tier1_unavg` it shows an amplitude overlay indistinguishable by eye, a −0.03 rad on-axis phase offset, and the 6.9e-2 difference localized at the beam center, which is the freshly radiated model-dependent part. The slice count comes from the Genesis4 file, so steady-state and time-dependent tiers both work.

The `weight_split` check is Fortran against itself. It exists because Genesis4 cannot test the weighted paths: its dump format has no weights, so every cross-code comparison sees the uniform case, where a bug like using one particle's weight for all is invisible. Collective observables are linear in the weights, so the split run must reproduce the unsplit one to round-off. The weight-dropping mutation fails this check at 2.4e-1.

### The tier2_bmad difference is a transport model difference, located and priced

The divergence localizes to the quadrupoles: after the first quad the bunching phase steps by 2.1e-3 rad while the transverse beam sizes still agree to 2.5e-11. The mechanism is the path-length term. Genesis4 advances theta through an interlude element as a single step whose path-length term `(px^2+py^2)/(2 gamma^2)` is sampled once, at mid element (transverse half step, then the theta step, then the second half, in `TrackBeam::track` + the `BeamSolver` drift case). Bmad's z advance integrates the same term exactly through the quad map. In a quad px changes substantially across the element, so midpoint sampling differs from the integral at the ~10 percent level of the ~0.01 rad px^2 contribution: the observed 2e-3 rad per quad. Through exponential gain and twelve quads this compounds to the 1.3e-2 power difference at saturation.

The proof is `tier2_genesis`: the identical build with only the interlude model swapped to the transcribed Genesis4 step collapses the difference by six orders of magnitude. Nothing else changes between those runs, so nothing else contributes at that level. Where the two transport models differ, Bmad's is the better one (the exact integral). The validation suite measures the difference against Genesis4. It does not prefer Genesis4's answer.

The residual budget for `tier2_genesis`'s own 1e-8 is rounding differences in the interlude theta advance. Genesis4 evaluates `ks*(1 - 1/beta_z)` per particle (a ~4e-9 cancellation carrying ~1e-16 absolute rounding) inside its RK4 bookkeeping. The transcription evaluates the same expression but sums the step differently. The RK4 collapses exactly when the slope is theta independent, and is collapsed. Multiplied by `ks*L` this is microradians of per-particle phase noise per interlude, amplified through gain. The per-particle theta medians say the same: 6.4e-14 rad for the typical particle, with a chaotic separatrix tail (see below).

### theta is reported, not checked

The final per-particle theta difference is printed with max, rms and median but does not check the comparison. theta is a bucket phase. At saturation neighboring trajectories separate exponentially, so the worst-particle difference measures Lyapunov amplification and not implementation quality. `tier2_genesis` shows it: median 6.4e-14 rad against max 2.0e-5. Its collective effect is checked, through the bunching curve and the final field.

### The validation suite bites

Mutations verify these checks. Dropping the factor 2 on the source term fails tier1 at 3.5e-1. Dropping the conjugation in the field gather fails at 2.8e-2. Using one particle's weight for every deposition, invisible to every Genesis4-based tier, fails the split-weight check at 2.4e-1. One sensitivity was knowingly traded away with the move to Bmad constants. The near-degenerate replacement of `sqrt(faw2)` by `faw` in the deposition is a 1.5e-10-level effect that the transcription-era 1e-10 check caught. It now sits below the 2e-6 constants floor and is not detectable by the Genesis4 comparison. Recovering that class of sensitivity is a job for Fortran-against-Fortran regression baselines (the weight_split pattern) and not for tighter Genesis4 checks.

The time-dependent checks were mutation-tested the same way. A slippage rotation that never fires fails td1 at 1.0e10 (elementwise per-slice power). Zeroing the wrong slice at rotation fails td1 at 1.0e9. Dropping the drift autophasing fails td2_genesis at 1.9e8. The fourth sensitivity is a measurement rather than a mutation. Guarding the end-of-lattice autophasing the way the mid-lattice case is guarded (one wavelength short on the final step) fails td1 at 0.84 of the final field, which is how Genesis4's unguarded `+1` on the final step shows. The elementwise per-slice power comparison is what makes these loud. A one-slice misalignment puts finite power against near-vacuum slices, so the failure signature is orders of magnitude and not percent.

The element-parameter path was mutation-tested the same way. A spurious `1/sqrt(2)` on the helical aw (the rms-convention error, exactly the mistake a translator would make) kills the gain outright and fails tier1 at 1.0 relative. Deriving helicity from the wrong attribute (element key instead of `field_calc`) fails identically. Removing the `b_max` assertion is caught by the refusal check. The lattice still dies, but on an unrelated downstream message instead of the assertion's own, which the check's grep rejects.

The thread-independence check catches its class too. Reintroducing a shared source accumulator across slices (the state of the code before the parallel step landed) puts the 1-thread and 8-thread runs apart by 7.0 relative in power, while the mutated 1-thread run is identical to the pristine one. That is the defining property of this bug class: invisible to every single-threaded check, every Genesis4 tier included, and caught only by comparing across thread counts.

(val-shot-noise-under-weights)=
## Shot noise under weights: the loader's noise is physical, and checked

The physics is in the manual, [](fel-physics.md#sec-loading).

A slice of current I represents `N_lambda = I*slice_spacing/(e*c)` real electrons, and physical shot noise means `<|b(h)|^2> = 1/N_lambda` per harmonic. The loader imposes it Fawley style, transcribed from Genesis4's `ShotNoise::applyShotNoise` and generalized to per-particle weights in one substitution. The electron count in the amplitude is the group's real charge over e, where Genesis4 uses the slice-uniform `ne/mpart` (identical for uniform weights). The algebra then gives `1/N_lambda` for any distribution of weight across the groups with no correction factors. Weights must stay uniform within a group. The quiet cancellation is per beamlet. Genesis4's silent `nbl < 1` clamp is kept but counted and warned.

The groups are the beamlets when the loader made them, else the particles sharing their transverse coordinates exactly, else the occupants of each deposit cell, and the rule used is printed. Before imposing, the loader measures the quiet floor `max_h |b(h)|^2 N_lambda` over every harmonic the beamlet structure can resolve (`1..beamlet_size-1`), and not just the imposed ones. An unquiet weight pattern can park its floor on a harmonic the imposition never touches, which this guard's own mutation test shows. Noise above 0.01 is refused with the value in the message.

Two permanent checks run in the validation suite:

- `check_shot_noise.py` (self-referenced): many-seed loading-only runs, `<|b(h)|^2>*N_lambda` against 1 within 5/sqrt(n) for harmonics 1-3, with uniform and with 0.25x/1.75x alternating beamlet weights. The same statistic runs on the loads that do not draw their own beamlets. Those are keep mode from a generated bunch, a bunch of copies made outside the loader (noise on the copies), and the same copies with jittered coordinates (noise on the deposit cells). Every group holds about 150 electrons. At 18 the kick is no longer linear in its amplitude and the scaled mean sits at 0.88 in every mode alike, which is the algorithm's own limit and Genesis4's too. The levels are in [](#val-levels-shot-noise).
- `check_sase_startup.py` (cross-code): dark start, one segment, each code generating its own noisy beam (fully independent loaders and RNGs), and the mean SASE startup power must agree. The ln ratio over 6 seeds x 32 slices is in [](#val-levels-sase-startup).

Each mutation fails the check built for it. Amplitudes from macroparticle count fail the statistical check at 13-20x. A slice-uniform electron count (weights ignored) passes uniform and fails the nonuniform mode at 1.52 (theory 1.5625). The within-beamlet weight mutation makes the guard refuse at 2.3e-1 against a 5.3e-5 target.

These two checks are statistical by necessity (independent RNGs). The `tdsase` tier is their deterministic complement. Genesis4 generates the noisy beam, writes it, and both codes track the identical realization dark through the full line, so startup from noise is also compared elementwise like any other tier. Both codes discretize the transverse plane and the load identically, and the tiers pin one grid and one particle count, so a dependence of the SASE power on either is invisible to them. It is measured in [](startup-noise.md).

The loader's own current profile reproduces the derived-current identity to roundoff, and a dropped $\sqrt{2\pi}$ fails that at 1.5. Importing the same Gaussian description agrees with it in rms of peak, which is a statistical comparison over 50k particles against a truncated-tail fit rather than an identity. Both levels are in [](#val-levels-import).

(val-the-load-path)=
## The load path: a bunch, sliced, quietened if asked, with noise if asked

The physics is in the manual, [](fel-physics.md#sec-loading).

The field file read as an import is checked against what a file written elsewhere may do and this writer never does. Samples stated in a unit other than V/m with `unitSI` carrying the factor, and a grid stated with `gridUnitSI` carrying the factor, must read as the file this writer would have written for the same field. The check takes a copy with its samples doubled and `unitSI = 0.5`, and a copy with its spacing halved and `gridUnitSI = 2`, and requires each re-dump dataset for dataset identical to the plain file's re-dump. Before the factors were applied the first loaded four times the power. A `y` component shaped unlike `x` is refused before it is read. The buffer is allocated from `x`, an HDF5 read has no bound of its own, and a wider `y` once wrote past the buffer's end, which the debug build caught and the production build reported as success. The source filter's angle becomes a cutoff in grid units. On the import path the conversion is taken from the file's spacing rather than from the grid keys of the input file, which an input file that imports its field need not state. Taken from the input file it was zero, every cutoff was infinite and the filter passed every mode while the header named the angle asked for. The check runs an imported field at two angles with no grid in the input file and holds that the fields differ, and that the input file without the grid keys filters as the input file with them. The check is `check_beam_format.py`, section `the field file as an import`, and the levels are in [](#val-levels-beam-format).

One path loads the beam from a bunch that `beam_init` generated or read through `beam.position_file`. `load_mode = "keep"` keeps every particle as a beamlet of copies at weight over `beamlet_size`. `load_mode = "sample"` loads the same count into every slice, by the analytic loader for a described bunch and by the resampler below for a file. `quiet_start` and `shot_noise` act on every load. `check_load.py`, in the validation suite, measures three exact identities and one statistical check, and the levels are in [](#val-levels-load):

- the keep load against the bunch, with currents, counts and charge-weighted moments recomputed with the same binning,
- the dump's charge at eight copies per particle,
- the split-weight invariance under coincident w/3 + 2w/3 copies,
- the in-cone startup of a Gaussian bunch in sample mode: the in-cone power summed over a window with slippage headroom, per 3 kA of summed current, against the flat window's interior mean of [](startup-noise.md), 0.133 MW.

The field record collects the emission of every beam slice it slipped past. For a bunch the per-slice power is therefore not proportional to the local current, and the comparable quantity is the sum over records, with 24 slices of headroom on each side so nothing escapes. The edge records carry 5e-8 of the peak.

Two loads are refused, each with the floor in the message: noise on the generator without the quiet start (floor 2.8e-1 against 0.01), and a bunch of copies whose phases were shifted singly (0.70). The unshifted copies load at 2.9e-28 with the noise on the particles sharing their coordinates. A slice dump named in `beam.position_file` is refused, since its slices would collapse onto one another.

(val-distribution-import-a-bunchstruct)=
## The resampler: a bunch_struct, resampled into slices

The physics is in the manual, [](fel-physics.md#sec-import).

The resampler is the `importdistribution` equivalent: an arbitrary bunch (arbitrary times, arbitrary weights) is resampled into the evenly spaced, equal-population slices the FEL step wants, by Genesis4's own method, transcribed from `SDDSBeam.cpp` into `fel_import_mod`. The class name is historical, since the file is plain HDF5. The bunch is Bmad's `beam_init_struct` made by `init_beam_distribution`: read from an openPMD-beamphysics file named in `beam.position_file`, or generated from the `&beam_init` description on the validation route `beam.resample.use_beam_init`, since a generated bunch otherwise takes the analytic loader. The driver can write any bunch back out as a Genesis4 distribution file (`t/p/x/xp/y/yp` + charge, with `t = -tau/c` so Genesis4's `s = -c*t` reproduces this port's window position exactly) and as openPMD-beamphysics (`hdf5_write_beam`).

Per slice: every particle inside a sampling window `dslen = slicewidth*bunch_length` (default 0.01 of the bunch, deliberately much wider than a slice) is a candidate. The slice current comes from the same window -- Genesis4's `count*dQ*c/dslen`, generalized to the weight sum `c*sum(w)/dslen`, identical for uniform weights and the only weighted generalization made. Candidates are brought to `npart/nbins` beamlet seeds by random deletion or by Genesis4's phase-space interpolation. That interpolation normalizes 5D to unit rms, takes the nearest original neighbor under a metric whose per-coordinate weights are fresh random draws, and places the child at the midpoint plus uniform[-1,1] times the difference. Theta is refilled over one beamlet spacing, mirrored into nbins bins, and the Fawley loader imposes shot noise with `ne = round(I*lambda*sample/(e*c))`. That is shared code (`fel_fawley_noise`), so the generator and the import stay one implementation. Genesis4's `match`/`center` transforms are *not* ported. They exist because Genesis4 lattices carry no optics, so an imported bunch must be rematched by hand. A Bmad lattice carries its Twiss and `init_beam_distribution` generates bunches matched to it already, so the transform would be a second way to say what the lattice says. For the same reason there is no namelist `gamma0` anywhere in the driver. The reference energy derives from the lattice's `e_tot`. A hand-rounded gamma0 against a round lattice energy once died mid-tracking on the seam's backstop p0c check, two specifications of one quantity. Two facts are pinned by reading Genesis4: the `align*` parameters are parsed but never used in v4, and the `shot_noise` flag is read but never consulted (the import applies noise unconditionally, skipping only zero-current slices). Both are kept as Genesis4 has them, and neither is transcribed as functional. one4one is out of scope: weights supersede it. Lucifer's own `shot_noise` switch is honored on this path as on every other, and an input file that wants the noise says so.

Validation (`scripts/check_import.py`, in the validation suite) splits along the RNG boundary -- exact checks where no random number enters, statistical only where one does. The exact checks are these, and the levels are in [](#val-levels-import):

- the per-slice current profile against Genesis4 importing the same file,
- the generated bunch's emittance against its specification,
- split-weight invariance under coincident w/3 + 2w/3 copies,
- the openPMD round trip through `beam.position_file`,
- thread determinism at 1 and 8 threads with the same seed.

The statistical checks are the slice Twiss and emittance recovering the specification over the central slices, and the dark-start startup power against Genesis4 with independent resampling RNGs.

Each mutation fails the check built for it. Normalizing the current by the slice spacing instead of `dslen` fails the exact current check at 6.5e-1. Skipping the shot noise fails the startup check at ln ratio -57 (a dead-quiet start). Collapsing the beamlet mirroring fails the startup check at ln ratio +4.7. Refilling theta over 2pi instead of 2pi/nbins is an equivalent mutant. Under the beamlet mirroring a uniform seed over the full turn is uniform modulo one beamlet spacing, the quiet cancellation is untouched, and the checks correctly pass it. It is a convention and not a defect class. The mirroring itself is the load-bearing neighbor, and that is what the mutation record covers.

With per-particle weights the resampling is optional. A direct weighted import (every bunch particle a macroparticle in its slice, no deletion, no interpolation) has no Genesis4 counterpart outside one4one and may be the better default once validated. Genesis4's O(n^2) randomly-reweighted nearest-neighbor interpolation is the first candidate for replacement. `examples/import/` is the self-contained demonstration: a beam_init bunch, matched by the import, tracked dark through the full line.

(val-slice-migration-under-weights)=
## Slice migration under weights

The physics is in the manual, [](fel-physics.md#sec-migration).

Genesis4 permits migration only under one4one, because with uniform weighting the charge a mover carries cannot be expressed. Per-particle weights dissolve the problem, and this port's coordinates dissolve the other half. z is continuous, the slice index is derived, and a one-slice move adjusts z by exactly `beta*slice_spacing` -- a phase shift of exactly `2*pi*sample`, so for integer `sample` the ponderomotive phase is continuous across the move to rounding. No wrap protocol exists to get wrong. `fel_migrate_slices` is the weighted generalization of `Sorting::localSort`: same criterion (`atar = floor(theta/slen)`), same swap-with-last removal, same rescan semantics. The MPI `globalSort` has no counterpart here by design. Particles leaving the window ends are dropped with their charge counted and reported per event. Genesis4 discards them silently at the world edges (`Sorting.cpp:194-195`). Migration is off by default (`migrate = true` enables). The Genesis4-comparison tiers run against Genesis4 without one4one, which never migrates, so enabling it inside a transcription-level comparison would be a model difference. The pass runs serially at a per-element stride between the parallel regions, so the thread-independence check is untouched. Per-slice `current` and `n_eff` are appended to the diag columns. N_eff drifts once particles migrate and is monitored, never assumed.

`check_migration.py` carries five permanent checks, self-referenced, and the levels are in [](#val-levels-migration). Charge conservation under heavy migration: a 60-m_ec² energy-spread beam, 74k moves, and in-window charge plus reported drops equals initial charge at every record. Exact phase continuity: the whole-beam weighted phasor obeys `S_before = S_after + S_dropped`. Window residency: every surviving particle's phase lies inside its slice window in the final dump, the routine's postcondition. No-op bit identity: a frozen-phase run with migration enabled reports zero moves and reproduces the disabled run byte for byte. The fifth is migration against the restored phase, which the phasing section below describes. An element displaced by a full carrier turn of `z_offset` keeps every particle, moves none, leaves none outside its window and gives the same phase as the zero-offset run.

The device runs migration through the same pass. With the beam resident at an element's last step, the pass reads the beam and the field back and releases residency, and the first four of those checks hold on the device run at the device's grid, the no-op exactly. The fixed-point deposit makes two device runs of one input file agree bit for bit, so the comparison that was once three times the spread between two identical runs is equality ([](#val-device)).

Each mutation fails the check built for it. Charge left behind on the move fails conservation at 8.9e-1. Leaving z unadjusted on the move survives conservation and continuity, because the mover cascade evaporates through accounted window-end drops, a balance that balances while the beam disappears. Window residency catches it (17 survivors outside). Removing the high-side bounds check dies on the constructed off-the-end mover with a bounds trap, never touching memory beyond the arrays.


(val-wakes-and-space-charge)=
## Wakes and space charge: kernels, convolution and the solvers

The physics is in the manual, [](fel-physics.md#sec-wakes) and [](fel-physics.md#sec-spacecharge).

Inside undulators and Genesis4-model interludes, the collective terms are transcribed at Genesis4's granularity (`fel_collective_mod`). Wakes act as a per-slice energy-loss rate. The three single-particle kernels are the resistive wall via the numerical impedance of Bane & Stupakov SLAC-PUB-10707, with AC conductivity and round/flat geometry, the undulator gap wake convolved with dI/ds, and surface roughness via the complex-q contour. They are superposed and causally convolved with the window's current profile, applied between the longitudinal advance and the second transverse half step, with theta held fixed through the kick. Longitudinal space charge enters as the per-particle `ez` in the pendulum equation, from the per-slice radial-harmonic tridiagonal solves plus the whole-window long-range term, both weighted (`c*w_j/slice_spacing` where Genesis4 has `current/npart`). The convolution is hoisted once, as Genesis4's is, and recomputed at every migration stride that moved a particle between slices or dropped one off the window's ends, since both change the currents. Every recompute appends a z-stamped eloss block to `<out_root>.wake.txt`, so the record shows the wake following the currents. The recompute once keyed on moves alone, so a stride that only dropped left the table computed from charge no longer there. `check_collective.py` builds that stride. A cold beam is confined to the head slice by editing a dump and detuned by 0.6%, so it slips off the head over two segments and never into another slice. The check holds one refreshed block per such stride.

What the short-range solve does with a degenerate slice is stated rather than left to the arithmetic. Its grid needs a radial scale: `space_charge.rmax` is a floor under it and the slice's own extent raises it. A slice whose charge sits at one transverse point offers none, and there is no scale to derive. The cell volumes go as the cell width squared, and the field of such a slice has no limit as the grid closes on it. That is not a zero either. Particles at one transverse point but different ponderomotive phases push each other, and only a lone particle feels nothing, its own harmonic sum cancelling term by term. The solve therefore refuses when it has no scale, at the slice where the state arises rather than only at setup, since migration reaches it by moving particles out of a slice until one is left. The refusal travels out through the advance to the walk, and the run stops before integrating from a force it did not compute. The solver's grid is also checked where it is stated. A radial grid of fewer than two points, a negative highest azimuthal mode, a negative harmonic count or a negative extent are each refused at setup, where before the first two ran and returned an exact zero with nothing said.

`check_collective.py` holds the five states the solve can meet, and the levels are in [](#val-levels-collective). A slice with no charge and a slice holding one particle each take exactly zero from the solve, in the mean and the spread against the same run with the master switch off. Two colocated particles at different phases open a spread while their mean moves a percent of that, which shows the force is mutual and not common. The no-scale case is refused, and so are the two configuration domains.

The long-range term's kernel, $(1 - |d|/\sqrt{d^2 + A})/A$ over the boosted separation $d$ and the slice's transverse area $A$, is evaluated as $1/[\sqrt{d^2+A}(\sqrt{d^2+A} + |d|)]$, the same quantity with the subtraction rationalized away. The two are equal in arithmetic and not in floating point. The first loses every digit once $A$ is small against $d^2$, and its $A$ in the denominator has nothing to cancel against when a slice's charge sits at one transverse point. A guard once put a square metre of area there instead, so such a slice radiated orders too little, and migration reaches that state by moving particles out of a slice until one is left. The rationalized form is the limit itself, $1/2d^2$, which carries the whole kernel to $q/4\pi\varepsilon_0 d^2$: the field of a point charge. `check_collective.py` leaves one particle in a slice, isolates its contribution by differencing against the same beam with that slice's charge zeroed, and holds it to that closed form on the three nearest slices. With the subtraction and the guard restored the same check reads 9.5e-1.

The short-range solve centers its radial bins and its azimuthal basis on the slice's charge-weighted centroid, which is what every term built on it is. Genesis gives every macroparticle the same charge, so its unweighted mean is its weighted one, and the transcription did not distinguish them. This port's weights differ within a slice. With the unweighted mean, replacing one particle by colocated copies whose charges sum to the original's, the same physical beam described with more macroparticles, moved the origin and changed the field at every physical point. `check_collective.py` splits one particle sixteen ways and holds every physical diagnostic to the unsplit run. Two controls pass either way: the same split with space charge off, and every particle split, which leaves an unweighted mean where it was and is why the validation suite's own beamlet loader never saw it. With the unweighted centroid restored the selective case reads 2.1e-5 and the controls stay at 1e-13.

Two decisions are recorded here as well as in the code. The numerical impedance is a separable routine (`fel_resistive_wall_wake`) because that computation is a future port target into Bmad proper as a wake source. The space-charge solver sits behind an interface a Bmad-slice implementation can later fill. Bmad's slice method is suspected the better model long-term, Genesis4's is transcribed now for consistency, and the comparison between the two is a future task.

Genesis4's collective code carries more truncated constants than its FEL core, and each tier's check is sized to the floor of the terms it enables. The tiers' own levels are in the tier table above:

| Term | Genesis4 constant | Floor | Measured tier |
|---|---|---|---|
| resistive/geometric kernels | `vacimp = 376.73` | 8.3e-7 | tdwk |
| roughness coefficient | `e = 1.6e-19`, `eps0 = 8.854e-12` | 1.4e-3 of that kernel | (inside tdwk) |
| long-range space charge | `eps0 = 8.85e-12` | 4.7e-4 | tdsc |

`check_collective.py` adds self-referenced checks. On a cold dark beam the wake is the only energy channel, and every record's `d<gamma>` must equal `eloss*dz/m_electron` exactly. The energy spread is invariant under the uniform kicks. Both levels are in [](#val-levels-collective). The diagnostics use a two-pass variance, since the one-pass form hid sigma-scale cancellation noise for as long as nothing moved the mean. Under heavy migration the eloss blocks must multiply and change, and the count is in [](#val-levels-collective).

Each mutation fails its named check. Reversing the convolution's causality (wake collected from trailing charge) fails tdwk at 7.0e-3, four orders above its pristine level. Flipping the sign of `ez` fails tdsc at 9.1e-1. Removing the migration-stride recompute leaves one eloss block and fails the stale-wake structural check.

Genesis4's `getSize` is the product $\sigma_x \sigma_y$, which the long-range term transcribes. A sum of variances in its place, $\sigma_x^2 + \sigma_y^2$, puts a 1.7e-1 error on the space-charge comparison.

(val-bmad-element-wakes-across)=
## Bmad element wakes across the whole bunch

The physics and conventions are in the manual, [](fel-physics.md#sec-seamwake).

Elements carrying Bmad `sr_wake` definitions (pseudomodes and the tabular `z_long`, binning plus FFT) act across the whole time window. For wake elements only, the seam concatenates all slices into one bunch in global window coordinates,

```
z_global = z_local + beta * (islice-1) * slice_spacing
```

-- higher slice index is the window head (larger Bmad z). The formula is the slice-migration invariant run backward (a mover's z shifts by exactly -atar*beta*spacing). The direction is pinned three ways: by that invariant, by the wake convolution (eloss collects `current(is+i)`, the wake trailing its source), and by the causality check. Interlude elements pass through Bmad's own `track1_bunch` (wake applied at `ds_wake`, Bmad's once-per-passage convention). FEL wigglers carrying `sr_wake` get one whole-window kick at the step nearest mid-element via `track1_sr_wake` directly -- a pure kick, no transport, with z rescaled by `beta_new/beta_old` to hold theta (the same convention as `wake_on`'s energy kick). Bmad's wake machinery is used as is: the seam supplies global z and charges, Bmad supplies the physics (`ix_z(1)` is the bunch head at largest `vec(5)`, `wake_mod.f90`). Two things are refused: lr (multi-bunch) wakes, and a pseudomode `z_max` or a `z_long` table extent `z0` shorter than the window (Bmad would kill the bunch mid-run). A Bmad drift cannot carry a wake at all (use a pipe), and the driver stops on any `bmad_parser` error rather than running a partial lattice. Wakes are resolved through lords (`pointer_to_wake_ele`): a wake on a superimposed or split element lives on the lord and `ele%wake` is null on its slaves. Checking `ele%wake` directly let a lattice's lord wakes fall through to the per-slice path, and the symptom was the zero-charge INFO line returning. Zero-length wake elements are kept in the walk for the same reason (a wake on a marker-like element is a standard Bmad idiom). A zero-length element is skipped only where Bmad tracks it as the identity: a marker, drift, pipe, instrument or monitor with no kick, no multipole, no aperture and no wake that can act. A thin kicker, a multipole, a patch or a zero-length cavity is tracked whatever its length. The rule is `fel_element_inert` in `fel_struct`, and the walk and the setup's record-count precompute both read it, as they both read `fel_interlude_wake` for which element's wake acts. Each once made its own decision, and the two disagreed twice. The walk skipped a zero-length kicker, dropping a kick of `1e-5` rad with no message. And with `bmad.sr_wakes_on` off the walk cut a wake-carrying element into pieces that setup had counted whole, so the run stopped at the stats writer with more records than the precomputed count. `check_diagnostics.py` holds a zero-length kicker to the same kick through a finite length at 1e-3, and cuts a wake-carrying pipe with the switch off.

The checks are in `scripts/check_seam_wake.py`, self-referenced, and every wake measurement is an A-B difference against a bit-identical no-wake run on a one-step wiggler, so the FEL evolution cancels exactly. The checks are these, and the levels are in [](#val-levels-seam-wake):

- the constant-pseudomode closed form (W = amp, self = W(0)/2) on the per-slice means,
- causality: the kick ahead of all charge must be exactly zero,
- the direction cross-check against `wake_on`,
- `z_long` against a first-principles particle convolution of the same table,
- the resolved-beam `z_long` against `wake_on`, under a per-slice bound derived from Genesis4's half-slice head deficit,
- split-weight invariance of the kick profile,
- thread determinism,
- lord resolution: a wake on a superimposition-split element applies exactly once.

The kernel bridge is `wake.write_kernels`, which exports the Bane-Stupakov kernels (eV/(m electron), s = 0 rows carrying the Bane self-slice half factor). A `z_long` table built from them gives the same physical wake through two independent implementations. The table is sign-flipped, since the transcribed kernels are stored as signed energy loss where Bmad's table is positive-decelerating, unhalved at s = 0, on the causal side z < 0, and zero-padded past the window. On the full 96-slice SASE line with a 0.5 mm copper chamber on every element (`examples/bmad_wake/`), the exit mean energy drop is -2.324 (Bmad z_long, once per element) against -2.308 m_e c^2 (`wake_on`, per step). The interior per-slice profiles agree to 0.7%. On a sub-slice-width bunch the two diverge by design. `wake_on` convolves slice density (Genesis4's model, linearly interpolated with a zero pad past the head, so half a slice of charge is missing at the window head), and `z_long` bins actual particles. The derived per-slice bound 0.5/(slices ahead + 0.5) brackets the measured differences at half its size.

Each mutation fails its check. Flipping the head/tail direction fails the closed form at 22 and causality at 2.8e-4. Dropping the slice offset (all slices coincide) fails both. Unwiring the charge fails the closed form at exactly 1.0 (kicks vanish).

Two bookkeeping identities ride with the seam wake. Energy bookkeeping, $d\langle E\rangle = \mathcal{E}\,\delta z$, holds against 203 eV kicks. The energy spread is invariant under a uniform kick, since a rigid shift moves the centroid and must leave $\sigma_E$ alone. Both levels are in [](#val-levels-collective).

(val-the-unaveraged-mode-fc)=
## The unaveraged mode: fc measured, not assumed

The ledger's closure depends on the order inside a substep, and the order was wrong for a field that diffracts. The source was added to the record after the diffraction. The beam was charged the cross term against the field the kick read while the record gained the cross term against the diffracted field, and the difference is first order in the substep's diffraction phase. The broad seed the ledger check used diffracts little in a substep and closed at 1.0e-5. A seed of 100 um waist left 1.2 percent of the turnover in the ledger at 20 substeps a period and 0.6 at 40. The source now lands on the record the kick read and the pair diffracts together, on the CPU, in the FP32 twin and in the device's solve, whose first pass lands the fixed-point source as it reads. The 100 um seed closes at 20 and at 40 substeps with no trend, and the broad seed closes as well, at the levels in [](#val-levels-unaveraged).

Closure is not order. The record the step advances is the substep's midpoint field, and the segment's own planes are half a substep from it. The record is therefore carried onto the midpoint at entry and back at exit, and a frame written inside the segment is carried back for the write. Before those carries the record kept its plane's name and not its plane. A fixed-grid refinement of a diffracting seed then converged at first order in the complex field and the particle energies alike, at 20 to 160 substeps a period. `check_unaveraged.py` refines the 100 um seed on a fixed grid and reads the error of each resolution against the finest. The field sits at 2.0e-8, 2.9e-9 and 6.8e-10 at 20, 40 and 80 substeps a period, the particle energies at 6.0, 0.38 and 0.024 eV. The observed orders between the resolutions are in [](#val-levels-unaveraged), with a floor of 1.7 on the first pair.

A frame written inside the segment is carried back onto its plane on a scratch copy, and the live record is not touched. The first version carried the live record back and forward again, two transform pairs whose rounding left 5e-15 of the field behind in the continuing run. Across 48 mixed-line cases with frames on against off no particle moved, and the field moved by that much. A diagnostic that steers the run it observes by a little is the same failure as one that steers it by more, so the copy is taken. The whole-window frame of an averaged element keeps its in-place rotation, which is a permutation and exact. `check_unaveraged.py` runs the mixed line with frames every 0.1 m, five of them inside the unaveraged segment. `check_device.py` runs the one-plane and two-plane unaveraged input files on the device and the CPU. Each holds the final beam and field identical to the bit against the same run with no frames.

The physics, conventions and provenance are in the manual, [](fel-physics.md#sec-unaveraged). MINERVA (Freund and van der Slot) is the published existence proof for this physics. Only its published work was used, and nothing here is compared against a MINERVA run.

`fel_method = unaveraged` is per element, so unaveraged segments mix with averaged ones in a single line. It integrates the particles through the undulator's real field, the full Newton-Lorentz quiver, by RK4 at `run.unaveraged_steps_per_period` (default 20, floor 10 on the convergence measured below). The radiation field enters as a Strang-split kick, and the source is built from the actual quiver current. Nothing from the averaged coupling path appears in it (the validation suite greps `fel_und_coupling|faw` out of the module), so the averaged mode's inputs become measurements. Entry and exit are sin² amplitude ramps (`run.unaveraged_ramp_periods`, default 2) with continuous slope, so the quiver vanishes at the segment ends where the averaged and unaveraged momentum conventions coincide. The beam carries a `quiver_in_px` convention flag that every averaged and seam entry asserts. In a mixed line those handoffs happen at real internal boundaries, and the sandwich check exercises them. The ledger is conserved on the middle segment, the mixed-against-averaged exit is compared, and a wake on the unaveraged segment is refused. The mode is parallel over slices with the averaged path's guarantees, and the validation suite checks that results are bit-identical across thread counts. Wakes, space charge and element wakes are refused. Each run writes `<out_root>.ledger.txt`.

`check_unaveraged.py`, in the validation suite, measures these, self-referenced or closed-form, and the levels are in [](#val-levels-unaveraged) and, for the frames, [](#val-levels-diagnostics):

- the energy ledger on the strong-seed probe, and on the 100 um seed at 20 and 40 substeps a period,
- the ledger's internal consistency, the kick side against the realized beam change,
- the order of the split,
- the ballistic dark run (B does no work), with the ramp handoff of emittance, orbit and mean px,
- fc against the closed forms for the planar and helical fundamentals and the planar third harmonic,
- the convergence of fc with the steps per period,
- the full-segment gain curve against the averaged default,
- a frame's own bunching and transverse centroid against the stats row's.

Two choices on merit depart from the references' conventions, and both are measured. The source deposits with `1/u_s` (and not Genesis4's averaged `1/gamma`), making kick and source exact energy duals. The ledger tightened 65× to the gamma-pz round-trip floor, while the period-averaged limit moves only ~5e-9. The magnetic push is explicit RK4 because fourth order is what makes fc measurable at the table's level with 20 steps/period. Its non-symplecticity is measured at gamma exact / emittance ≤ 3.3e-6 over the longest Benchmark1-SASE segment (266 periods, 5320 steps), and the ballistic check holds it should production-length unaveraged runs appear.

The JJ Bessel factor and its h=3 counterpart emerge from the raw dynamics at the level in [](#val-levels-unaveraged), the first independent check on `fel_und_coupling`'s closed forms, and on the harmonic-load rule. The beamlet quiet start cancels every harmonic below `beamlet_size`, so `nbins = 8` is quiet at h=3 and no quadrature load is needed for this measurement. The h-probe is the same undulator with the field at `lambda1/h`: the mode is harmonic-agnostic.

Each mutation fails its named check. Flipping the E·v kick sign fails the ledger at 2.0 (energy created) and the gain comparison at 0.69, while the magnitude-blind fc checks pass it, which is why the ledger is check zero. A hard-edge entry (`run.unaveraged_ramp_periods = -1`, the explicit sentinel) fails the orbit-handoff check at 3.2e-5 m, 19 sigma of the probe beam. Note: the exit momentum re-absorbs the quiver at integer-period lengths, so the orbit, and not the exit mean px, is the reliable instrument. Skipping the exit handoff flag is refused at the first seam element.

The ramp phase jump at each segment end compensates the slippage the ramps lose against the hard-edged contract. Without it, the per-segment ln-power deviation against the averaged mode over the six segments of the Benchmark1-SASE line is 0.0000, +0.08, +0.005, +0.02, +0.01 and +0.13. The first segment is immune, since nothing is bunched yet. Compensating continuously inside the ramp instead costs -0.9% gain on the first segment, doubling with ramp length, so the jump is discrete and at the ends.

## Two polarizations: vector radiation, tilt honored, the crossed undulator

The radiation carries (Ex, Ey) when any FEL element is tilted (`UNDY: UNDX, tilt = pi/2` is a y-planar undulator, standard Bmad, no new attribute), when the seed is y-polarized (`seed_polarization = 'y'`), or when the field read from `field.file` carries both planes. Otherwise Ey is never allocated and the single-component path runs untouched (every tier bit-for-bit, the compatibility keystone). The third condition was once missing. The state was decided at lattice setup from the first two. A restart from a y-polarized field under an input file that stated no seed polarization then allocated one plane in the stats and the device and wrote past it at the first record. An imported field now decides its own planes, and the refusals that depend on the state are made again after the import. The check restarts a y-seeded helical run with and without the seed's polarization and holds the two diag files byte identical. Kick and deposit act through each element's polarization 2-vector (planar: (cos t, sin t), helical (1,+i)/sqrt2). The unaveraged mode needs no polarization code at all, since its real per-particle currents work against and deposit into their own components. One openPMD dump holds both polarizations as components x and y of its mesh record, and the stats file carries field/total, field/x and field/y under the same dataset names.

The helical handedness is checked with seeds of both circular polarizations, since a total power cannot tell them apart and the dark-start comparison of the scalar and vector paths never could. A cold, nearly chargeless beam through the helical probe is driven by a uniform seed three ways: as the scalar envelope, as the pair (1, +i)/sqrt2 and as the pair (1, -i)/sqrt2 of the same total intensity. Each runs in the averaged mode and the unaveraged one. In each mode the co-rotating pair reproduces the scalar seed's rms energy modulation, and the counter-rotating pair leaves a small residue of it. The residue is smaller in the averaged mode, which carries no beat between the two rotations, than in the unaveraged mode, where the beat averages to nothing over whole periods and the ramps leave that much. The levels are in [](#val-levels-two-polarization). The averaged vector once carried (1, -i), so the two modes selected opposite handedness from one field. A seed that drove the averaged element left the unaveraged one unmodulated, and a mixed two-plane line radiated the two elements into opposite circular polarizations. The unaveraged mode's Lorentz force, which needs no vector, is the authority the averaged vector follows.

- the rotation identity in both modes: an all-y line fed the swapped beam equals the all-x line,
- the beam-size swap identity,
- the crossed undulator: the x field's gain isolation through the y set, and the y field lighting up from carried-over bunching,
- the averaged against the unaveraged crossed y-power,
- the unaveraged time-dependent ledger over both components,
- 1 against 8 threads on the crossed time-dependent run,
- the helical re-anchor, vector against scalar path on shot-noise power.

Tilt on a helical element and tilt with the transcribed maps are refused.

The rotation identity uses the driver's `swap_beam_xy` check instrument (the RNG draws its planes sequentially, so the generated beam itself is never swap-symmetric).

The helical re-anchor, which rotates the reference polarization basis and must return the same field, closes at the level in [](#val-levels-two-polarization).

(val-harmonic-fields-and-the)=
## Harmonic fields and the openPMD wavefront

The walk carries an ordered set of radiation fields, Genesis4's `vector<Field*>` shape, with the fundamental always entry 1. A harmonic field h (namelist `harmonics = 1, 3, ...`) lives at wavelength lambda_1/h and enters the physics in exactly three places. Those are its coupling fc(h) (the Bessel factor, zero for every harmonic of a helical device), the harmonic ponderomotive phase h*theta in kick and deposit, and its own diffraction kernel and escape accounting. In V/m no other factor appears. Genesis4's per-field ks factors are its internal unit conversion, absorbed once. Harmonic fields start dark and grow from the beam's bunching, or import. Nonlinear harmonic generation is `examples/harmonics/`, where P3 grows from a dark start under a 200 MW fundamental over 4 m. The example's page carries the harmonic's exit power in its table of what the run measured ([](generated/examples/harmonics.md)). A single-entry set is the pre-harmonic walk bit for bit (the two-polarization overlay discipline again). Harmonics with two live polarizations, and with an unaveraged element, are refused, so unvalidated combinations refuse rather than guess.

Dumps speak one format, openPMD, in both directions. A field dump is an openPMD EXT_Wavefront file (`.wf.h5`), both polarizations as complex components of one mesh record (h5py reads them as complex128 natively), one file per harmonic with photonEnergy identifying it, and a harmonic's file carrying `-h<h>`. The standard document is authoritative: the validation suite verifies every required attribute against its text independently of the writer. A file that is not openPMD is refused on import, with the conversion command in the message, and `tests/scripts/convert_genesis.py` converts either kind of file in either direction. The Python side of the round trip is openPMD-beamphysics's own `Wavefront.from_openpmd`/`write_openpmd`, exercised against the Fortran writer and reader on every run of the validation suite.

One format rather than a choice of formats is a decision, and its cost is one conversion step in the validation suite. The Genesis4 reference chains write their own dumps, and the validation suite converts them once per chain before the tiers read them. What that buys is that no writer in the physics code has to hold a second chart, no input file names a format, and every dump carries the per-particle weight.

check_harmonics.py, the validation suite's harmonics section, measures these, and the levels are in [](#val-levels-harmonics):

- the planar steady-state tier against Genesis4, on the fundamental power and on the dark harmonic-3 growth,
- the one-step dark deposit's P3/P1 against the exact Bessel sum,
- the converter's Genesis4 view of a dump, in complex values,
- the Fortran openPMD read-back and re-dump,
- the Python Wavefront class's energy through its Genesis4 path, and its own openPMD read and round trip,
- the Fortran reader on the Python writer's file,
- 1 against 8 threads on a time-dependent harmonic run.

Six refusals are matched by message: no anchor on the fundamental, an unaveraged element, two polarizations, the frequency domain, an import matching no field, and the Genesis format.

(val-phasing-between-segments-measured)=
## Phasing between segments: measured, then built

The offset and the migration are checked together, since each alone was checked and the pair was not. The migration checks ran without an offset and the phasing checks without migration, and the migration at a displaced element's last step read the displaced phase. On eight cold, nearly chargeless slices behind a 0.1 m break, a full carrier turn of `z_offset` (25.8 mm) moved every particle one slice and dropped an eighth of the charge. The survivors sat outside their new slices once the phase was nominal again. The offset is now returned before that migration. `check_migration.py` runs the four cases, offset on and off against migration on and off, and holds every particle kept, no moves, every particle inside its window, and the offset run's phases against the zero-offset run's ([](#val-levels-migration)).

Between undulator segments the default is Genesis4's behavior, measured before anything was written. Scanning an inter-segment gap by fractions of 2 gamma^2 lambda (25.8 mm per turn on the Benchmark1-SASE line) leaves the bunching phase entering the next segment flat on Genesis4 and on this code alike. Segments are autophased, so the fractional drift slip never reaches the coupling. The deliberate off-phase knob is the wiggler's own `z_offset` (standard Bmad misalignment, anchored at the nominal position). A displacement delta shifts the entry phase by exactly -2 pi delta/(2 gamma^2 lambda). The same scan run as Genesis4's own PHASESHIFTER element reproduces this code's curve and the exit power against phi at the levels in [](#val-levels-phasing), so the phase reaches the physics identically and not just the bookkeeping. The PHASESHIFTER needs finite length to register, since a zero-length one silently does nothing. Both codes track the same Genesis4-written initial dumps there. On independently loaded beams the same comparison sits at 1.4e-4, which measures the two loaders and not the phasing. There is no new element and no new attribute.

With `bmad_com[absolute_time_tracking] = T` in the lattice (honored per element through Bmad's own resolver), phasing follows the real spacings instead -- the recirculating-linac discipline. A wrong-length break visibly detunes the next segment, and the absolute-mode gap scan reproduces the relative-mode z_offset scan point by point. Chicanes work in both modes: the beam detours the closed bump via the seam while the radiation drifts the chord between undulator faces (from ele%floor, derived never entered). The arc-minus-chord delay becomes whole-slice window rotations plus, in absolute mode, its carrier phase. examples/chicane/ flips a second segment between 1.32x gain and 0.94x absorption on 0.43 urad of bend angle -- half a wavelength of geometric delay.

check_phasing.py, the validation suite's phasing section, measures these, and the levels are in [](#val-levels-phasing):

- the re-anchor baseline: the gap scan flat, in radians of span,
- the `z_offset` knob against -2pi delta/(2 gamma^2 lambda),
- the cross-mode identity: the absolute gap scan equals the relative knob scan,
- this code's knob curve and exit power against Genesis4's PHASESHIFTER, on shared dumps,
- the chicane in relative mode (the geometric fraction dropped) and in absolute mode against an independent 2D geometry,
- the 2D trace against the small-angle closed form theta^2(2L_b/3 + L_d),
- the unaveraged ledger's closure across the chicane,
- the time-dependent chicane's extra banked slices against floor(delay/lambda) at three delays,
- the time-dependent chicane at 1 against 8 threads.

Four refusals are matched by message: an open bump, a genesis-model bend, an oversize `z_offset` and a `z_offset` on the first element.

The time-dependent chicane's targets sit mid-interval, at 3.5, 6.5 and 10.5 wavelengths of delay. At exactly 3.000 wavelengths the 6e-8 difference between the exact trace and the small-angle form decides between 2 and 3 banked slices. A delay of 2.99 wavelengths banks 2 slices and one of 3.01 banks 3, which places the walk's floor where the trace puts it.

(val-spontaneous-emission-the-two)=
## Spontaneous emission: the two FEL modes against Bmad's own radiation

This check is Bmad-only, with no Genesis4, since the averaged mode's Genesis4 agreement is settled by the tiers. `check_spontaneous.py` in the validation suite tracks one short helical wiggler (`tests/bmad/spont_probe.bmad`, 40 periods, Benchmark1-SASE parameters) and the same beam four ways over 0.6 m. The four are Bmad's own `runge_kutta` with `radiation_damping` on the same wiggler, `runge_kutta` with radiation off, the averaged FEL mode and the unaveraged FEL mode. The reference is the analytic rate `(2/3) r_e γ² k_u² a_w²`, which is the coefficient in Genesis4's `Incoherent.cpp`. The levels are in [](#val-levels-spontaneous).

Bmad's radiation damping reproduces the analytic rate, and the same integrator with radiation off loses nothing, so the reference is independent and not in doubt. The two FEL modes then say something specific:

The averaged (KMR) mode does not charge the beam at all. Its step adds `2S` to the field while the particles are kicked by `E`, so the `4|S|²` part of the field-energy increment is created rather than taken from the beam. That is the model and *not* a defect. Genesis4 carries an optional `&sponrad` module (`doLoss`/`doSpread`, off by default) precisely to add the missing loss and diffusion by hand. The check pins it as a known zero, so a future change that starts debiting the beam cannot pass unnoticed.

The unaveraged mode conserves energy by construction, so its beam pays, but only for the radiation the grid can hold. An SVEA grid represents angles to the FFT Nyquist θ_max = λ/2dx. The evidence that the captured fraction is acceptance-limited undulator radiation is its scaling. Varying only the acceptance (ngrid 64/128/256 at fixed box, θ_max = 0.79/1.6/3.2e-5 rad) moves the captured loss 0.21% -> 0.82% -> 3.32%, and the measured-to-predicted ratio of that move across a 16x range in captured solid angle is in [](#val-levels-spontaneous). The absolute normalization sits ~3x below a dipole-limit estimate of the angular distribution, which is that estimate's own accuracy at a_w ~ 1. The test therefore checks the shape tightly and the magnitude loosely.

Both FEL modes honor Bmad's global switches `bmad.radiation_damping_on` / `%radiation_fluctuations_on`, set directly in `[run]`, which exposes `bmad_com` the way Tao's `&tao_params` does. Interludes always honored them through track1. The same instrument measures these with the switches on, and the levels are in [](#val-levels-spontaneous):

- damping in the averaged mode against the analytic rate,
- damping in the unaveraged mode against the ramp-and-capture composite, 0.9703 of analytic, since the explicit term integrates the ramp envelope and the grid-captured self-field adds on top,
- the fluctuation growth of sigma in both modes against the Saldin form, and against Bmad's `runge_kutta` with fluctuations,
- 1 against 8 threads with fluctuations on, with serial per-beamlet draws in fixed slice order,
- the unaveraged time-dependent ledger with radiation on, E_beam + U + U_esc − U_spont + E_rad over the turnover.

Fluctuation kicks are one draw per beamlet, exactly as Genesis4. Independent per-particle kicks would break the quiet start's per-beamlet harmonic cancellation, and fluctuations with slice migration is refused for the same reason. Genesis4 reaches the same variance with uniform x sqrt(3) draws. Lucifer's draws are Gaussian, the physical limit. With the switches off (the default) every tier and check is unchanged bit for bit. The measurement that first exposed the gap was a dark segment where the averaged model's field gained 134x what its beam paid. Fluctuation growth is measured on a cold beam, since with a real energy spread the sigma^2 differencing drowns in cross-covariance sampling noise.

(val-the-coherent-source-simplex)=
## The coherent source (SIMPLEX hybrid)

`run.source_model = "coherent"` swaps the per-particle source deposit for Tanaka's coherent retrieval (PRAB 27, 030703 (2024), implemented from the paper). The spatially incoherent part of the bunching, whose per-cell sampling noise makes under-populated runs overestimate gain, is dropped from the source. The coherent part deposits as an analytic Gaussian carrying the slice's exact source phasor, centered and tilted by phasor-weighted moments (this port's extension) with Tanaka's kappa width fit. The field, gather, and every diagnostic are untouched. `"deposit"` stays the default and the reference the coherent model is measured against.

check_coherent.py, the validation suite's coherent-source section, measures it. At M = 128/slice the plain deposit fakes gain on a curve that truly absorbs, and the coherent source stays at the model's own bias, measured at the large-M reference. That is a 64x particle reduction, and the levels are in [](#val-levels-coherent-source). The guard is per-slice Gaussianity against sampling significance, weighted by charge. The model is refused with the unaveraged mode, with harmonics, with two polarizations and on a dark start. On a dark start the coherent model comes out ~175x low, since spontaneous spatially incoherent emission dominates SASE startup and the coherent model drops it, so seeded runs only. One more thing was measured once: SIMPLEX's coarse stepping (12 periods/step) costs 2.6e-3 in |ln P| here (taper and harmonics untested at coarse steps).

(val-the-programs-own-identities)=
## The program's own identities

Three invariances of the driver follow, none of them physics, each one a way a rewrite could break the tracker silently.

The library never stops. Every error returns through `err_flag` and the program decides, so `tests/lucifer_smoke_test.f90` drives the whole library with no input file anywhere and reproduces an input file run dataset-identically. `track_fel_line` is re-entrant, and twice in one process is bit-identical to two processes.

A windowed run composes with the full one. `run.track_start`/`track_end` bound the walk, but the schedule (slippage, autophasing, break geometry, including the end-of-lattice fixup) is always built on the full lattice. So `[start, D]` followed by `[after D, end]` from its dumps reproduces the one-shot run to the dump format's own round-trip floor, measured 3e-13 and held at 1e-10. The walk itself is bit-for-bit, and a windowed run's finals equal the full run's mid-line dumps exactly.

That composition check runs steady state, where slippage is a no-op, so a time-dependent restart follows it, across a boundary chosen so the field record has slipped half a slice past its last rotation. A restart has three kinds of state to work from:

- Preserved by the files: every particle's coordinates, its lag with the reference phase folded into the file's time, its weight and its id (openPMD's `id` record through `ix_user`), and the slice partition through `particlePatches`. The field's complex records are rotated to time order, with the rotation index `first` folded in, plus `slippageResidual`, the signed slippage in fundamental wavelengths not yet rotated. A dump at an eligible boundary also carries the checkpoint group `lucifer` on both files ([reading-output](reading-output.md)). The group holds the reference phase $\varphi_0$ and every particle's $z$ as the tracker holds them, beside the folded records and changing none of them, with the position and element the frames were written at.
- Rebuilt by setup: slice membership from the partition, the start position from the window's entry face, the wavenumber and phase rate from the lattice, and the chamber wake's loss table from the loaded currents. At an element end those are the post-migration currents, since migration runs at an element's last step.
- Reset, as historical totals a continuation does not need: the escaped energy, the spontaneous and radiation sums, the migration and drop counts, and the stats record count.

Migration and the chamber wake are checked across a restart. Migration derives a particle's destination from the whole phase, $\varphi_0 + k_s z/\beta$, floored over the window's $2\pi\,$`n_wavelength`, and the dump folds exactly that phase into the file's time. A decision therefore carries across a restart unless a particle sits nearer a slice boundary than the error in its reconstructed phase. Each row of the migration file records the smallest such distance any particle examined at that event had, the dropped particles included. The check reads it against the phase error the continuation has propagated to the frame before the event, particle by particle by id. The case is a beam that migrates and drops through three undulators, checkpointed at the first pipe's end after 1569 moves and 6.3e-17 C dropped, with a residual of 2.00004 wavelengths. The three later events had margins of 4.6e-4, 1.8e-3 and 3.6e-3 rad against propagated phase errors of 3.1e-13 to 7.3e-13 rad, a factor of 1.5e9 or more. With the margin cleared, exact identity holds. Ids, slice populations and membership are identical at all 62 frames. Every later event matches by position and move count with the dropped charge equal to the digit. Since the checkpoint the moves (1308), the dropped charge and the escaped energy agree, the last to 3e-26 J on 6.0e-13 J at the footer's full precision. The field and energies sit at 6.6e-13 and 1.5e-13. With the chamber wake on, the restart rebuilds the loss table in force at the checkpoint from the surviving charge to the digit. It refreshes the table at each of the three later events, at the same positions and to the digit, the same summation running on the same currents on both sides. A separate case shifts every restarted phase by a little less and a little more than the smallest recorded margin. Shifting by 0.9 of it flips no decision, and by 1.1 of it moves one particle differently at the first event, which is what the margin means, and that case establishes nothing about equivalence. Bmad short-range element wakes are checked the same way. Such a wake acts once per passage through the whole window. The concatenation adds each particle's slice offset to its longitudinal coordinate at that particle's own entry $\beta$, Bmad kicks the assembled bunch, and the split subtracts the offsets back. All of it is scratch of one passage, so a checkpoint at an element end carries what the next passage needs. What a restart has to place correctly is the kick itself, and the check takes both sides of it. A checkpoint before the wake element has a continuation that must apply the kick. One at that element's end has a continuation that must not apply it again, since the dump already holds it. Which passage applies the kick is read from the runs rather than assumed, as the first frame whose beam departs from a wake-off history. For a wake a superimposed marker has split onto a lord, that is the slave holding the lord's midpoint, `PW#1` of the two. Every restart runs against the same full lattice, so lord ownership is reconstructed identically.

An unaveraged segment boundary is checked the same way. (val-parallelism-openmp-over-slices)=
## Parallelism: OpenMP over slices, bit-identical by construction

Slices are independent within an integration step. The only cross-slice operations are slippage (an index rotation, applied serially between steps) and the per-beam `phi0` advance (one scalar, computed before the loop). The slice loops of `fel_track_und_step` and `fel_track_interlude_genesis` are therefore plain `parallel do` regions, and the work of the parallel step was making the per-slice step safe to run concurrently:

- The FFTW plan cache in `wavefront_mod` is threadprivate: each thread owns its plans and its aligned work buffer. Plan creation stays inside a named critical section (FFTW's planner is globally serialized), while plan execution touches only the calling thread's buffer.
- The field-solve kernel (`fel_k2`) is built once, serially, by `fel_field_kernel_init` before any parallel loop, and is read-only ever after. `fel_field_step` errors on a mismatch rather than rebuilding, so nothing writes module state inside a parallel region. The source accumulator is a local of `fel_field_step`, one per invocation.
- The Bmad-seam interlude loop runs one slice per thread. `track1_bunch`'s own particle-level region (`track1_bunch_hom`, on by default via `global_com%mp_threading_is_safe`) nests inside it and runs serial per thread with nesting off, the OpenMP default. With radiation fluctuations on the loop stays serial, since the draws come from one shared RNG stream whose order must stay fixed.

Because each slice's arithmetic is identical regardless of which thread runs it (no cross-slice reductions exist in the step loop), the result is bit-identical across thread counts, and the validation suite checks that. The time-dependent single-segment configuration reruns with `OMP_NUM_THREADS=8` against the 1-thread run, requiring the diag file byte-equal and every dump dataset exactly equal. (Whole-file `cmp` of HDF5 would false-alarm on object-header timestamps. The comparison is per dataset.)

The scaling was measured on the full 6-FODO line, 32 slices x 2048 particles (Apple Silicon, debug build):

| Threads | Wall time | Speedup | Efficiency |
|---|---|---|---|
| 1 | 129.6 s | 1.00 | the reference |
| 2 | 74.4 s | 1.74 | 87% |
| 4 | 46.4 s | 2.79 | 70% |
| 8 | 32.6 s | 3.97 | 50% |

It saturates near 4x at 8 threads. Two parallel regions are spawned per integration step, and on this machine 8 threads includes efficiency cores. With 32 slices there is also little schedule slack: 4 slices per thread at 8 threads. Production-size runs (hundreds to thousands of slices) have more parallel work per serial byte, so this is the floor of the scaling rather than its ceiling.

[](performance.md#perf-thread-scaling) measures the same curve at 96 slices in a production build and gets 7.00x at 8 threads and 9.59x at 12, which holds that claim. It also measures what the serial fraction is made of. The slippage rotation is 0.3% of the walk, the per-slice diagnostics reduction runs slice-parallel, and every phase this file can name totals 0.5%, so the rest is the cost of entering a parallel region.

### Head to head against Genesis4 at 12 workers

One command reproduces this measurement on any machine:

```
./tests/run_perf_benchmark.sh
```

It detects the performance-core count (`--workers N` to override) and sizes the window to 4 slices per worker so Genesis4 does not pad. It finds the MPI launcher that matches the Genesis4 binary's own linkage, since an OpenMPI `mpirun` aborts an MPICH-linked genesis4 on sight. It times all four runs with one external clock, and refuses to print a table unless the two codes' answers agree at the documented seam level first.

The measurement is a 48-slice run, full line, 2048 particles per slice, identical starting dumps, production/release builds on both sides, on an M3 Max with 12 performance cores. The slice count is divisible by the worker count, so Genesis4 does not pad its window. The answers agree at the documented seam level (4.0e-2) before any timing is quoted:

| | Serial | 12 workers | Parallel speedup |
|---|---|---|---|
| Genesis4 (MPI) | 152.7 s | 35.8 s (12 ranks) | 4.3x |
| `lucifer` (OpenMP) | 123.6 s | 19.4 s (12 threads) | 6.4x |

The tracker is 1.2x faster serial and 1.85x faster at 12 workers. The parallel gap is the cost of communication. Genesis4's 12-rank run spent 68 s of system time on the per-step MPI slippage ring exchange and diagnostics gather, where this code's slippage is an index rotation in shared memory and costs nothing to communicate.

(val-the-particlepath-cost-measured)=
## The particle-path cost: measured, two levers adopted

A real 42 m case (131 slices) at 2048 particles/slice ran at parity with Genesis4 (96 vs 94 s, 12 threads vs 12 MPI ranks, same machine back-to-back). At 8192/slice it did not (164 vs 99 s). The per-element time stamps and an in-wiggler profile put the gap in one place: the FEL step's particle path (the RK4 + gather), whose cost quadrupled with the particles while the per-slice field FFTs (~68 s) stayed constant. [](performance.md#perf-the-transform-length) measures that crossover as a table, and [](performance.md#perf-the-phase-profile) is the standing phase profile every run's own footer prints.

`programs/lucifer_advance_bench.f90` (built as `lucifer_advance_bench`) times the path serially at fixed state -- measured (min-of-5, this machine): full fel_advance 152 ns/particle-step, the RK4+ODE alone 87.5, the four sin/cos pairs the ODE evaluates 48. A clang -O3 twin of the same verbatim RK loop runs 68 ns, and its sincos loop 13.7 ns. The gap is codegen and libm rather than physics (macOS gfortran has no vectorized libm and emits scalar calls).

Two changes were adopted as one value change, since each pays nothing alone and together full fel_advance drops to ~108-125 ns and the real case 164 -> 143 s:

- per-file `-O3` on `fel_track_mod` (CMakeLists `set_source_files_properties`), and
- the paired-sincos shim (`code/fel_sincos.c`): one libm call for the (sin, cos) pair at the ODE's three call sites.

The change is at the 1-ulp level. gfortran's sin/cos intrinsics differ from libm's sincos by one ulp on ~2e-6 of arguments (measured: 73 mismatches in a 44M-point sweep of the theta domain. The C-side test of __sincos against libm sin/cos was clean, so the divergence is gfortran's intrinsic lowering), and -O3 re-contracts floating arithmetic. Per the tier contract, the full validation suite re-ran and every tier holds its Genesis4 tolerance. Four recorded values moved at the ulp-amplified level (tier1_unavg 6.934012e-02 -> 6.933979e-02, tier2_genesis 1.772017e-05 -> 1.771895e-05, tdsase 2.292890e-06 -> 2.292906e-06, weight_split 7.917158e-13 -> 3.508953e-13). The other seven are unchanged.

The interludes (the seam) track slice-parallel where they can. The per-slice track1_bunch loop runs one slice per thread (coarse granularity instead of per-particle inner threading), bit for bit at any thread count against the serial baseline (checked at 1 and 8 threads on tier2 and td2). Two boundaries remain, both deliberate. Radiation fluctuations keep the serial loop, since they draw from the one shared RNG stream inside track1, whose order must stay fixed. Wake-carrying elements were always whole-window concatenations (manual [](fel-physics.md#sec-seamwake)), so lattices whose interludes all carry wakes see no change. Note: the scratch bunch is block-local inside the loop body and *not* an OMP `private` variable. gfortran left a `private` copy of the allocatable-component derived type improperly initialized (a deterministic 2x bunching shift, present even at one thread), while a block-local declaration gets Fortran's own default initialization.

The production (-O2) and debug (-O0) trees were never bit-identical to each other (FP contraction). The bit-for-bit keystone is a within-tree contract, and the validation suite runs the debug tree. The remaining gap to Genesis4 on the 8192 case (143 vs 99 s) sits in the per-slice field FFTs and the wake-path interludes. The clang-twin numbers bound what further particle-path codegen work could still buy (~68 ns vs ~125 per particle-step).

## The source filter, against Genesis4's own

The angular filter on the source term ([](fel-physics.md#sec-source-filter)) is a transcription, so it is checked the way every transcribed path is. Both codes run the same configuration from the same particles and the same field, and what is left over is transcription fidelity. Genesis4 4.6.15 carries the filter as `source_filter`, so the reference exists. The chain is the pure-SASE input file with the filter on at Genesis4's own defaults, `xcut = ycut = sigmoid = 1`, which puts the sigmoid's half-height at twice the Nyquist angle, off the grid, so the filter is the sigmoid's soft roll-off alone. The same input file with the filter off is the `tdsase` tier.

| Run | Line | Window power at the end | Relative to Genesis4 | Worst over records |
|---|---|---|---|---|
| Filter on, `xcut = 1` | 12 undulators | 32.739 MW | 1.80e-06 | 2.18e-06 |
| Filter off | 2 undulators | 43.927 MW | 1.26 | 1.28 |
| Mutation: the sigmoid on the field instead of the source | 2 undulators | 4.722 MW | 0.757 | 1.28 |
| Mutation: the sigmoid's edge at twice the cut | 2 undulators | 21.428 MW | 0.101 | 1.08e-01 |

The filtered run lands at the `tdsase` tier's own level against the same reference chain with the filter off ([](#val-levels-source-filter)). The filter is transcribed to the fidelity of the path it sits in.

The three rows below it are what give that number its meaning. The unfiltered run differs from the filtered reference by order one, so the filter is what moved the answer and the comparison is sensitive to it. Both mutations leave a run that completes and a power curve that stays plausible, since a sigmoid on the field suppresses wide angles too and an edge at twice the cut is the right shape in the wrong place. The second mutation moves both cuts together, and its level doubled when it stopped leaving `ycut` at Genesis4's default. Only the reference separates them. Each of the three is wrong from its first step, so each stops at the second undulator. A full line would cost four times the section for no more evidence. The check is `tests/scripts/check_source_filter.py`, section `source-filter`, and its tolerance stands in [](#val-levels-source-filter) as the bound.

On the device the filter takes a different route to the same quantity. The CPU multiplies the sigmoid onto the source inside the field's own transform pair, which it has to spare. The device's fused solve adds the source in real space in its last pass, so the source is filtered in place first by four passes of its own and the solve is left exactly as it was. The two are compared on a time-dependent 256-point input file of eight slices. Genesis4's reference chain is a 255-point grid and the Metal solver takes powers of two, so the device cannot join the Genesis4 comparison, and a 64-point grid carries almost no emission beyond the edge for a filter to remove. The window power agrees and the filter removes wide-angle power, at the levels in [](#val-levels-device). The mutation hook is the CPU check's own and the device refuses it, since it carries no second solve to make wrong. The check is `tests/scripts/check_device.py`, section `device`.

(val-fp32-lockstep)=
## The FP32 particle path, priced by lockstep

Apple GPUs have no FP64, so a single-precision form of the averaged FEL advance exists as a measured object before any kernel. An FP32 twin steps beside the FP64 path from a shared state at `fel_advance`'s own sequence point, and `run.fp32_check` records the per-quantity divergence (`fel_fp32_mod`, [](input-reference.md#param-global-fp32-check)). The twin carries the three reformulations FP32 forces, each documented in the module header with the quantum that forces it. Energy is an offset from the reference, since the FP32 quantum of absolute gamma is 1.35e-3 against a per-step change of 3.0e-4. Phase is a residual with the base rotator evaluated in FP64 once per slice. The detuning is a difference of like small quantities, since the FP64 ODE's square-root argument is 1 minus ~1.3e-8, which is exactly 1 in FP32 and erases the phase equation.

The longitudinal residual needs a moving reference, and the instrument's own guard found that. The split is $z = z_{ref} + dz$ with the reference one FP64 number per slice. On the instrument's first run the reference was static, the beam's common $z$ drift accumulated into the residual, and at step 514 of 1068 the guard refused the run at 28 ulps against its floor of 32. A secular term in the residual is quantized away silently, so the reference follows the slice's FP64 mean each step, one host number per slice. In freerun mode the persistent residuals rebase across the move with `fel_fp32_renorm`, the same operation migration needs, and the round trip is in [](#val-levels-fp32-lockstep).

The field solve has its own twin: the deposit scattered into an FP32 source grid, FFTW's single-precision transform pair, and the propagator rounded from the FP64 kernel, applied to the twin's own field record each step. Two rows join the stream, the source grid and the post-solve field, both against the FP64 post-solve field's norm. In freerun the FP32 field carries across steps, fed by the twin's own deposit and read by its own gather. The twin is then a complete single-precision run beside the FP64 one, longitudinal and field state alike (the transverse maps stay FP64 and enter rounded). A freerun window is one slice by refusal: the twin keeps no slippage rotation of its own. That transform is FFTW's own single-precision interface, and the build detects it rather than assuming it. The conda toolchain carries `libfftw3f` and the off-site distribution's from-source FFTW is double precision only, so a build without the library refuses `fp32_check` instead of transforming in a precision other than the one it reports.

The lockstep levels, worst over the run per quantity, are in [](#val-levels-fp32-lockstep) for a steady state of 2048 particles over 57 m through saturation and for a SASE window of 96 slices x 2048 over the full line. The freerun row, which no check records, is below (M3 Max, production build, and the debug build agrees):

| case | pz (relative) | theta [rad] | phasor (of full charge) | source | field | guard [ulp] |
|---|---|---|---|---|---|---|
| freerun (compounding), steady state | 1.8e0 | 3.3e1 | 2.1e-1 | 4.0e-2 | 1.3e0 | 2.2e3 |

The lockstep rows are the per-step cost of FP32, and they are flat across a run because the state refreshes each step. The source and field rows agree to three digits, so the deposit's FP32 phase noise dominates the step and the single-precision transform contributes beneath it, consistent with published transform-only figures of 2.2e-7 to 4.0e-7. The transverse rows measure representation only (~6e-8, FP32 epsilon), since the transverse maps stay FP64.

The end-to-end number, the one a device port is judged against, is below:

| case | exit power (relative) | exit bunching (absolute) |
|---|---|---|
| freerun, one 3.99 m segment, exponential gain | 1.0e-3 | 2.9e-8 |
| freerun, 57 m steady state, deep saturation | 2.7e-1 | 3.6e-2 |

The gain-regime figure sits at the order of the published backends' end-to-end SASE comparison (6.7e-4). The deep-saturation figure is a different quantity. Past saturation the power oscillates with the synchrotron rotation, and an FP32 trajectory ends at a visibly different phase of that oscillation. A 27% instantaneous power difference at one z is what phase decorrelation looks like there, with the bunching magnitude off by 3.6e-2 on 0.185. A device port validated per step by this instrument's lockstep rows is not exposed to that compounding. A device run trusted end to end through deep saturation is, in FP32, and the number is on record.

The validation suite's section `fp32-lockstep` holds these, and the levels are in [](#val-levels-fp32-lockstep):

- the lockstep levels inside the recorded ceilings,
- the residual guard healthy,
- the bucket renormalization round trip,
- the FP64 outputs untouched with the instrument on against off,
- the mutation moving the theta level and the source row,
- freerun compounding past lockstep on the phasor,
- the freerun end-to-end power divergence on the gain segment,
- the instrument stream at 1 against 8 threads,
- the refusal of a wake with the instrument on.

The instrument is read-only on the physics by construction and by check: nothing outside it reads the FP32 state, and the instrumented run's FP64 outputs are byte-identical to the uninstrumented run's. Configurations this twin does not cover (harmonics, two polarizations, the coherent source, wakes, space charge) are refused rather than half-measured. The unaveraged mode has a twin of its own, [](#val-unaveraged-fp32).

(val-device)=
## The Metal backend, judged by the instrument

Slippage on the device keeps the fundamental's bookkeeping for every member of the field set, and the energy it transmits out of the window is stated in the footer per member, since the unaveraged ledger was otherwise its only reader. The device's own routine once formed the transmitted slice's light time from the member's wavelength alone, where `sample` counts fundamental wavelengths. A third harmonic's escaped energy then came out a third of what left the record, while the surviving field and the window power were right. The routine takes the harmonic number as the CPU's does. The check holds the device's escaped energy to the CPU's on the time-dependent harmonic input file: the fundamental to six digits and the third harmonic at the level in [](#val-levels-device), against the factor of three the defect gave. The check is `check_device.py`, section 7c.

`run.device = "metal"` runs the FEL step on an Apple Silicon GPU ([](input-reference.md#param-global-device)). The seam is one C interface (`device/lucifer_device.h`) behind `iso_c_binding`, one Objective-C++ file behind that, and a stub that refuses on every other platform, naming the toolchain it would need. No Metal type or call appears anywhere else, so a second backend is a new implementation of the same interface plus one CMake branch. The design is this project's own prior work, the Genesis 1.3 v4 backends on branch `gpu/metal-engine` (commit 4919b01, unmerged upstream). The transform kernels, the one-command-buffer step and the buffer-sync rule transcribe `MetalEngine.mm` from that branch. The physics kernels transcribe Lucifer's own `fel_fp32_mod` twin and the Bmad transverse map, so the arithmetic the device runs is the arithmetic the lockstep instrument already measured.

The source deposit is the second place this backend carries fixed point, and for a different reason. Float addition is neither associative nor commutative, so a deposit that adds atomically into a cell answers differently depending on the order threads arrive. Two runs of one input file differed by 2.0e-7 on a field power and 1.6e-8 at the exit. That is far inside the band against the CPU and is not an accuracy problem. But it costs every device output the right to be compared exactly, which is why the migration no-op was once measured against the spread between two identical device runs. Integers do not have that property. The deposit accumulates in ticks of a power-of-two scale and converts once where its first consumer reads it. That is the first of the filter's source passes when the filter is on, and the solve's last pass when it is off, since nothing transforms the source then. Sixty-four bits are carried as two 32-bit words, this hardware having no 64-bit atomic of any kind. Every low addend is unsigned, so the carry count is a property of the sum rather than of the order. Thirty-two bits would not serve. A scale that keeps the worst case inside an int leaves a quantum that loses to the float accumulation it replaces by a factor of seven. Sixty-four bits beat it by the same factor, and the four configurations in the table below hold at the float deposit's own levels. The bound is every macroparticle of the run in one cell in phase at an eighth of the lowest gamma the run loaded. That gamma is measured over the beam rather than assumed of the reference, and the eighth is then margin for what tracking can take off a particle, which is of order rho and a thousand times smaller. The run's charge gives the bound at setup, the element's source scale and the roll-off complete it at the first step, and the scale, that origin and the headroom are printed there. On the Aramis segment the scale is 2^24 ticks per volt per metre against a bound of 2.7e11 V/m, and the quantum sits below the FP32 spacing of the bound by the margin in [](#val-levels-device).

The roll-off is the kernel's own and not a simpler stand-in for it. The kernel takes the particle's offset from the undulator axis, rotates it when the segment is tilted, and forms the roll-off from that. The bound therefore takes the box half width plus the axis offset and puts the whole of that radius against the larger of the two curvatures. Bounding each axis at the half width with no offset and no rotation is short by up to four and a half in the roll-off term and about twelve percent in the bound.

That floor is checked in the kernel, where the deposit happens. A readback cannot do it. It sees the state at an element's last step, so a particle is free to cross the floor and come back before anything looks, and a breach found there is found after that element's deposits have already used the bound. The kernel tests every particle before its contribution is converted or accumulated, drops one that fails, and records a fault that survives to the next drain. The test is written so that a gamma which is not a number fails it. On seeing the fault the host stops the run at that readback, which is ahead of any stats row, dump or exit line drawn from the step, so nothing computed across a breached interval is written. Raising the floor above the beam demonstrates it: the run exits non-zero, names the floor and the lowest gamma read back, and writes no output file. Guarding in the kernel also covers the twin, which is never resident and whose readback a host check never reaches.

What the quantum contributes is measured rather than bounded. The deposit's scale can be shifted by whole bits, which moves the quantization and leaves the phase and the FP32 arithmetic beside it alone, so the source row's composition can be read off directly. On the cancelling-phase input file the row at the derived scale is in [](#val-levels-device), and it is the same to every digit with the quantum 24 bits coarser, a factor of sixteen million. It first moves at 26 bits coarser, to 1.0100x, and reaches 1.0505x at 29, which is the last shift the headroom refusal allows. So the floor of eight bits sits where quantization begins to cost a few percent, and at the thirty-seven bits the derivation delivers it costs nothing the row can resolve. Both ends are asserted, the row unmoved at 24 bits coarser and the run refused at 30.

Two refusals guard the scale, and they guard different things. The headroom refusal catches a quantum that would not beat the float accumulation it replaced. It cannot catch everything, because the scale is chosen against the same bound the headroom is measured against, so their product always lands in one binade and the headroom reads 37 bits whatever the input file. No input file reaches that refusal, and raising the minimum past 37 is what fires it. What the headroom cannot see is a scale the kernel cannot hold. The scale and its reciprocal reach the kernel in single precision. A bound below about 5e-20 volts per metre sends the scale past the largest float, and a bound above about 4e56 sends its reciprocal there. Either would deposit through an infinity with the headroom still reporting 37 bits. Both are refused explicitly. Neither is reachable by an input file with charge in it, the tested input files sitting some thirty orders inside the nearer edge, and the refusal is demonstrated by forcing the scale past what a float holds.

One deliberate divergence from the reference backend is stated where the citation is: the longitudinal state is a 64-bit fixed-point phase and not an absolute FP32 theta, in ticks of $2\pi/2^{32}$ off a static FP64 per-slice reference. The low 32 bits are the phase modulo one radiation period at a uniform 1.5e-9 rad, the high bits count whole periods, and a bucket crossing is exact integer arithmetic. The uniform quantum is what lets the reference stay static for a whole element where the FP32 residual of [](#val-fp32-lockstep) needed a moving one. Bucket wraps are modular arithmetic and are asserted exactly, on the device's own arithmetic at every setup. A bucket shift and its return must be bit-exact and the extracted phase must never see the shift, a statement no tolerance is allowed to soften.

The backend is judged by the lockstep machinery with the device in the twin's role. `device = "metal"` with `fp32_check = "lockstep"` leaves the FP64 run untouched (diag byte-identical, on against off). The device advances every step from the shared pre-step state, whole -- its own transverse maps, push, deposit and field solve -- with the rows in the same `.fp32.txt` stream. The ceilings are three times the recorded CPU-twin levels above, absorbing that Metal's precise-math sincos is not libm and its fused ops round differently. The transverse rows get their own recorded levels, since the CPU twin refreshed those from FP64 and the device runs its own FP32 maps. A jump against the refreshed reference is a kernel bug by definition. The measured levels, worst over the run, are in [](#val-levels-device) for a steady state of 1024 particles and for a SASE window of 8 slices x 1024 with slippage live. They were taken on an M3 Max, both builds agreeing, on the check cases of `check_device.py` at grid 64.

The guard column is the median per-step phase increment in ticks of the fixed-point quantum. Its floor plays the same silent-z role as the residual guard above. The mutation hook reaches the kernels themselves. `fp32_mutate` perturbs the detuning resonance inside the shader by one part in $2^{12}$ and coarsens the uploaded phase. The theta and source levels each move by well over a decade, so the ceilings catch a wrong kernel constant and not just a wrong upload.

End to end the two roles corroborate each other. The freerun twin (state resident and compounding, single-slice window) lands on exit power against the CPU run's diag rows. The production run (`fp32_check` off, the device is the run, beam and field resident through each element with readbacks only at the stats comb's positions) lands at the same level on the same input file. That is the freerun-measured order reached twice by different routes, and the levels are in [](#val-levels-device). Wall times against the CPU are in [](performance.md#perf-device), with the dispatch floor stated.

The validation suite's section `device` holds these, and the levels are in [](#val-levels-device):

The field set rides the device whole. Every harmonic member and both polarization planes are resident, stored member-major with one propagator per member, and the step's constants carry each member's harmonic number, coupling $f_c(h)$ and deposit scale plus the element's polarization pair. The push gathers every member at $h\theta$ and sums them into every RK stage, `fel_ode_multi`'s structure in the FP32 reformulation. The deposit writes every member's source at $e^{-ih\theta}$. The transform runs over every plane with its member's propagator, and the polarization factors apply at the field add as `fel_field_step` writes them. Every member rides the one fixed-point phase, at $h$ times it, so the exact-wrap assertion covers the set, and every plane slips together. With one member and one plane every kernel is the single-field arithmetic it was, term for term, and the eleven recorded levels above did not move. Harmonics together with two live polarizations is refused for the device as for the CPU.

The instrument judges every member. The device twin fills the phasor, source and field rows as the worst over members, so the stream keeps its ten columns and its ceilings, and the footer adds each member's own worst for attribution. A member's phasor and deposit are compared at $h\theta$ through `fel_fp32_deposit64` unchanged, and every member's source and field rows are normalized by the fundamental's field, the run's power scale. That normalization is a measured decision. A harmonic's own norm cannot serve, because on a quiet start the CPU cancels the harmonic bunching to FP64 roundoff while the device's FP32 phase leaves it at $\sim 10^{-7}$ of the charge. The first attempt read 6 to 8 on a deposit whose end-to-end power agreed at $10^{-3}$. The harmonic's fidelity lives in its phasor row, which needs no field normalization, and in the end-to-end harmonic power against the CPU.

That floor is the one thing the set does not resolve, and it is recorded. The device's harmonic bunching error is $\sim 2\times10^{-7}$ of the charge, three times the fundamental's phase error as $h = 3$ predicts. Where the harmonic's true bunching sits above that, the device is right. The shot-noise time-dependent window puts $b_3$ at $1/\sqrt{N}$ and the device lands on $P_3$ against the CPU at the level in [](#val-levels-device), and a strongly bunched beam lands there too. Against one time-dependent Genesis reference with shot noise, imported by the CPU and the device alike at grid 64, the device lands on $P_1$ and $P_3$ at the levels in the same table, above the CPU's own. Where the true bunching sits below the floor, the device radiates the floor instead. On the planar steady-state tier input file with a quiet start and a dark third harmonic, whose $b_3$ is $\sim 10^{-8}$, the device's $P_3$ is 139 times the CPU's while $P_1$ holds its band. No guard refuses that case, because the same configuration with a strong seed bunches the beam past the floor within the segment (`examples/harmonics/` climbs nine decades and agrees at 4.6e-4). The phasor row states the floor per member, and a user compares it with the bunching the run is after. Steady-state Genesis holds no shot noise, which is why the reference here is time dependent.

Slice migration runs with the device resident, and no kernel is involved. `fel_migrate_slices` touches no field and runs serially on the host at an FEL element's last step. When the beam is resident there the pass reads the beam and the field set back first and then releases residency, since the host is then authoritative and the field came back with it. The comb readback and the element end that follow find nothing resident, so the readback moves rather than doubles, and the next element uploads the re-sliced beam. Migration grows a slice's arrays, and the device's particle buffers are a rectangle sized at setup to the largest fill. An element entry or a twin step whose largest fill exceeds the capacity grows the rectangle, growth only and without a shader recompile, and says so in the run's output. The checks are `check_migration.py`'s own input files at the device's grid. Conservation and phase continuity hold on the device run by construction, since the pass runs on read-back arrays, and the check proves the order. The run migrates past 73,000 moves with conservation and continuity at the levels in [](#val-levels-device). The heavy-migration window's exit power against the CPU is in the same table. The lockstep instrument runs on a migrating time-dependent input file with the twin re-staging every step across the changed fills and the capacity growing under it, and the ten rows sit inside the ceilings above at the single-field levels. The no-op check is byte identity on the device as it is on the CPU, the fixed-point deposit having made two device runs of one input file agree bit for bit. A frozen-phase run with migration enabled reports zero moves, its final beam matches the migrate = F device run exactly, and two migrate = F device runs match each other exactly. One property of the instrument is recorded here. The source and field rows normalize by the slice's own post-solve field. On a quiet-start input file without shot noise every slippage feeds the tail slice a field at FP64 roundoff, so those rows read 0.4 on a deposit whose end-to-end power agreed at 4e-4. The input file the check runs carries a seed and shot noise, as the time-dependent lockstep input file above does, and the rows read what the table records.

One property was inherited from the reference backends and no longer holds here. Their deposits accumulate with device atomic adds whose ordering is not fixed, so two runs of one step differed in the source's last bit or two, and no device output could be asserted byte-identical against another device run. The fixed-point accumulator above ends that, and the two-run comparison covers every array of the statistics file. Everything the kernels do not cover is refused at setup or first use, and a build without the backend refuses the knob itself with the stub's own message. Which build that is comes from detection rather than from the platform. The backend needs macOS and a Clang-family Objective-C++ compiler, since it is ARC-managed Objective-C++ against the Metal framework, and a macOS build whose Objective-C++ compiler is a GNU one takes the stub like any other. The configure output names the backend it built, and a capability-free build was measured to produce byte-identical physics to a full one.

## The unaveraged mode on the device

The mode resolves the undulator quiver, so a record step is `nsub` Strang substeps of half magnetic push, radiation kick with its source deposit, half push, and the slice's own diffract and source add ([](fel-physics.md#sec-unaveraged)). Three kernels are the mode's own and everything else in the step is the kernels the averaged path already had.

What is reused carries most of the step, which is why the port is small. The four-pass solve, the accumulator's clear, the fixed-point deposit's scatter, the residency and staging, and the tick phase chart with its exact-wrap assertion are unchanged. What is new is the quiver-resolving push, the kick with its deposit, and the ledger's spontaneous reduction. Their share of the device's own seconds is measured in [](performance.md#perf-device-unaveraged), and it moves with the load exactly as the CPU's split does: 34% of the device time at 512 particles a slice and 57% at 4096.

Three quantities do not depend on the particle and are built in FP64 on the host, once a substep rather than once a particle, which is the hoist `docs/performance.md` measures. The envelope $g$, its slope, and $\cos(k_u s)$ and $\sin(k_u s)$ at the four RK stage positions of each half push arrive as eight `float4` a substep. The optical carrier's base $e^{i\Psi_\text{mid}}$ arrives per substep per slice, reduced modulo $2\pi$ first, since $\Psi_\text{mid}$ reaches some 1700 radians over a segment and no float carries that. The propagator $\exp(K_2 \delta)$ is the entry `fel_field_diffract` reads, at the substep rather than at the record step.

The lag is the one state variable of the push that no other line reads: $d\tau/ds$ depends on $\gamma$, $u_x$ and $u_y$ alone. The push therefore integrates it from zero over a substep and adds the increment to the 64-bit tick accumulator, so the lag is carried exactly and no arithmetic ever differences the increment against a lag that grew. That is what the FP32 twin of [](#val-unaveraged-fp32) could not do, and its guard on the residual is the measurement of what it cost there. The residual's own quantum overtakes the per-substep change on a long window, where a tick is $2\pi/2^{32}$ of a radiation period whatever the window. The kick then reads the lag as an angle in $[-\pi, \pi)$, where FP32 spacing is finest, exactly as the averaged push reads its own.

The deposit's bound is this mode's own. A contribution here carries $|j|/u_s$ where the averaged deposit's carries a roll-off over $\gamma$, so the bound is the run's whole charge times the largest ratio the kernel is allowed to meet. The quiver sets that ratio. $|j|$ reaches $\sqrt{2}\,a_w$ at the peak of a planar wiggle, the betatron momentum adds a hundredth of it on the checked input files, and $u_s$ falls no lower than the gamma floor the device measured at setup. One rest momentum of headroom on the numerator covers a transverse momentum no FEL beam has. The kernel checks the ratio on every particle and refuses the run through the same fault the averaged deposit's gamma floor uses, so the bound is checked rather than assumed. On the check's input files the scale lands at $2^{26}$ ticks per V/m against a bound of $6.6\times10^{10}$ V/m, the quantum below the FP32 spacing of the bound by the same margin as on every input file ([](#val-device), [](#val-levels-device)).

The encoder shape is the averaged step's, repeated. One record step is one command buffer holding eight dispatches a substep: the accumulator's clear, a half push, the kick with its deposit, a second half push, the ledger's reduction and the solve's four passes. One more dispatch a record step takes the energy baseline. A 60-substep step therefore encodes 481 dispatches and an 89-step segment past 42,000, which is why the per-pass instrument commits early many times over on this mode and says so.

The readback cadence is the comb's for the beam and the field, as it is on the averaged path, and one record step for the ledger. The stage factors and the carrier rotators are host writes into buffers the device is reading, so the command buffer drains once a record step before they land. The ledger's two terms are read there because that drain has already been paid. The device is busy for three quarters to nine tenths of the walk on every input file measured ([](performance.md#perf-device-unaveraged)), so the drain is not what this mode waits on.

The ledger's two terms cross the seam differently, and neither reduces with a float atomic. $\gamma$ changes only in the kick, exactly, so the record step's beam-energy change is $\sum w (\gamma_\text{end} - \gamma_\text{start}) m_e$ and the host forms it in FP64 from two readbacks in its own order. The spontaneous term $4\sum|\text{src}|^2$ has no such shortcut and reduces on the device. One threadgroup owns one chunk of one slice and one accumulator slot, reduces its chunk in threadgroup memory over a fixed pairing, and adds the result into its own slot as a compensated pair. Nothing is contended, so the arithmetic runs in one order, and two device runs of one input file give one answer. The check holds that on a time-dependent window at 4 threads against 8.

The measured levels are worst over the run, with the device in the twin's role on one Aramis segment at grid 64 and 1024 macroparticles a slice, 89 record steps of 60 substeps. Ceilings are three times the first measurement, `check_device.py`'s own convention. The rows are the transverse pair and the momentum pair in the quiver chart, pz, theta, the phasor, the ledger's source column, the field and the guard in ticks a record step. They are taken on a steady state and on an 8-slice window. The FP64 diag and ledger are byte identical with the twin on against off, and the production exit power is held against the CPU. The levels are in [](#val-levels-device).

The theta row is better than the CPU twin's and the phasor row better than its ([](#val-levels-unaveraged)), which is the tick chart's own doing. The ledger row is wider on the window because it is scaled by the energy the record step turned over, and on a dark-start shot-noise window a slice can turn over almost nothing.

The mutation moves what it reaches. The hook coarsens the uploaded lag accumulator by 65536 ticks, which is $9.6\times10^{-5}$ rad, and the residual angle the kick reads. The phasor, theta and field rows each move by more than a decade, and the moved levels are in [](#val-levels-device). The transverse rows do not move, and they should not: $\gamma$ changes only in the kick, so a phase perturbation reaches $x$ and $p_x$ at second order. The hook was once a no-op in the shader, returning its argument unchanged. It took its step as a fixed fraction of the argument, which makes the ratio the same integer for every argument.

What this mode's ceilings are set by is arithmetic that predates it. An FP32 forward transform, propagator multiply and inverse transform lose about $1.3\times10^{-7}$ of the field's energy every time they run, systematically and in the same direction, where the FP64 pair drifts by $1.6\times10^{-12}$ over 5340 applications. With the charge set to $10^{-30}$ C, so that the repeated diffract is the only thing acting on the field, the loss is $-1.273\times10^{-7}$ a pair at grid 64, $-1.295\times10^{-7}$ at 128, $-1.499\times10^{-7}$ at 256 and $-1.787\times10^{-7}$ at 512. That is roughly linear in the butterfly stage count. The averaged mode runs the pair once a record step and a 12-segment line therefore loses $1.4\times10^{-4}$ of the field energy, which sits under every ceiling that mode records. This mode runs it `nsub` times, so one 89-step segment of 60 substeps loses $7.2\times10^{-4}$, and on the weakly seeded steady input file that is the whole of the exit power's divergence from the CPU ([](#val-levels-device)). The check measures the per-pair loss on both input files and holds it in a band, so a pair that stopped being nearly unitary would show. The rate those four grids give is about 0.17 of an FP32 quantum a butterfly stage over the $2\log_2 n$ stages of a pair, $1.22\times10^{-7}$ to $1.83\times10^{-7}$ against the measured $1.27\times10^{-7}$ to $1.79\times10^{-7}$. The run header counts the pairs a field record sees over the line, substeps included, and projects the loss from that rate: 5340 pairs and $6.5\times10^{-4}$ on the one-segment unaveraged input file, 89 pairs and $1.1\times10^{-5}$ on the averaged one. The check holds the count to the input file's and the projection within a factor of two of what the same run measured. The rate is one machine's fit to four grids, which is what the factor of two allows for.

The unaveraged energy ledger therefore does not close on the device at the level it closes on the CPU, and the reason is that loss rather than the port. On the CPU the ledger closes at $4.2\times10^{-6}$ of the turnover. On the device it cannot close better than the transform's accumulated loss. On an input file whose per-record energy exchange is comparable to one FP32 quantum of the field's own energy it says nothing at all. The ledger input file of `check_unaveraged.py` has a per-record $|dU|$ of $1.1\times10^{-18}$ J against a quantum of $2.0\times10^{-18}$ J on a field holding $3.3\times10^{-11}$ J, and a single-precision ledger cannot resolve an exchange that small, whatever the port does. The ledger's internal consistency, the kick-side column against the realized beam change, does hold on the device: 2.8e-6 against the CPU's own level in [](#val-levels-unaveraged), since both sides of that comparison come from the same FP32 energy offsets.

The frame series rides the comb here as it does everywhere. The comb's positions are where the resident state comes back to the host, so a frame is written from arrays the readback refreshed rather than from stale ones. The check holds that: with `dump_at_comb` on, a device run writes the same nine beam frames and nine field frames the CPU run writes, at the same $s$ exactly. What a frame must carry is the chart. A frame taken inside the segment holds the undulator quiver in `px`, which is a common offset of order $a_w/\gamma$ and reaches the value in [](#val-levels-device) where the averaged chart sits near 1e2. `felMethod` names the chart, so a reader cannot mistake one for the other. The comparison is on the mean and not the spread, since an rms is blind to exactly the quantity the chart adds. The device's mean tracks the CPU's at the level in the same table, which is the FP32 round trip of the chart rather than the transform loss that sets the power band above.

Two live polarizations ride the device in this mode as they ride the CPU. The mode needs no polarization vector, since the two real kinetic momenta work against and deposit into their own field components. The kick gathers both planes with the same four weights, fills a source plane for each, and each plane meets the diffraction with its own source. The crossed line is the input file, an x set then a y set, and its rows sit inside the one-plane ceilings ([](#val-levels-device)), the field row both planes summed. The FP64 stream is byte identical with the twin on against off, the mutation moves the rows it reaches, and in the production role the x plane agrees with the CPU at the level in the table. The y plane carries 1.3e-4 of the x plane there, the afterburner's transfer, and agrees at a few percent of its own value. That is what single precision does to a weak coherent transfer, and it is far from the 1 a plane that went dark would read. That case occurred: the second plane's propagator once asked for a member the kernel buffer does not hold, and its record came back an exact zero while the first plane and the field's total stayed in family. The transform pair costs the set what it costs one plane, since the loss is each plane's own, and the two losses are in the table.

The handedness the mode selects is checked on the device, since a total power cannot tell two circular polarizations apart. A cold beam through the helical probe is driven by a uniform seed as the scalar envelope and as each circular pair of the same total intensity. The device reproduces the scalar seed's rms energy modulation with the pair (1, +i) near the CPU's own level, and leaves the beam unmodulated with the pair (1, -i) at the CPU's own residue to three digits. The levels are in [](#val-levels-device) and [](#val-levels-two-polarization).

Harmonics, wakes, space charge and the coherent source are refused for the mode on both. `fp32_check = "freerun"` stays refused for the mode, since freerun compounds a single-precision state across steps and this twin carries none.

## The unaveraged advance in single precision

Apple GPUs carry no FP64, so this project's rule is that a single-precision form of an advance exists with its divergence from the FP64 path measured before any kernel is written for it. The averaged advance has one, [](#val-fp32-lockstep). The unaveraged advance has one too. Without it nothing could judge a device port of that mode, since `fp32_check` refused the mode outright.

The twin advances every substep of a record step from the state that step received, and the comparison is read where the record step ends. That granularity is a choice with a reason. A substep is internal to the integrator, where a record step is the point the FP64 path and any device port synchronize, so the twin measures what a port would have to match. The FP64 run is untouched, which is asserted: the diag stream and the ledger are both byte identical with the twin on against off.

Single precision destroys four things in this advance, each measured on a real mid-segment state rather than argued from the formula:

| quantity | the naive form | what it costs |
|---|---|---|
| slippage rate, `gamma/u_s - 1/beta0` | both terms are one to within 1.3e-8 | the difference is 1.9e-9, which is 0.016 of the quantum of one, so it returns exactly zero and the slippage is gone |
| energy, gamma | 11358, quantum 9.8e-4 | the per-substep change is 1.0e-6, a thousandth of a quantum |
| lag, tau | quantum grows with the window | the per-substep change is 3.1e-12 m, resolved at 4.4e5 quanta on one slice and 0.84 on a 351-slice window |
| phase, Psi | carried whole per particle | 2.7e-5 rad at a segment's end, growing with s |

The forms that replace them are the offset charts the averaged twin already uses, `goff` and a per-slice residual, and a base phase held in FP64 one number a slice a substep. For the slippage the form is the identity `1/ra - 1/rb = (a - b)/(ra rb (ra + rb))`, which moves the cancellation into a difference of two small like quantities and is exact rather than a series. `u_s` needs no reformulation at all, which measurement settled against expectation. `sqrt(gamma^2 - 1 - ux^2 - uy^2)` does lose the 1 and the `ux^2` entirely, but they are 6.7e-9 of the result, so the naive and the reformed values agree to 5.0e-8.

Two of those are mutation records and not arguments. Replacing the slippage identity with the naive difference takes the phase row from its level to 1.7 rad, a factor of 170,000, and 1.7 rad is comparable to pi: the bunching phase is meaningless. Storing gamma absolutely instead of as an offset takes the energy row to 2.0e-4, two decades up. The field row has its own. Dropping the factor of 2 the substep's source carries takes it to 1.3e-2, a factor of 2200, so a wrong constant in the twin's field arithmetic lands well above the level the row is held to.

The measured levels are worst over the run and worst of the two builds, which agree on every row to a few percent (M3 Max, the Benchmark1-SASE segment at 2048 macroparticles and grid 128, 89 record steps of 60 substeps). The rows are the transverse pair, the transverse momentum pair in the quiver chart, the energy, the phase, the phasor, the ledger (the twin's energy against the step's) and the field (the twin's record after every substep against the step's). The FP64 diag and ledger are byte identical with the twin on against off. The levels are in [](#val-levels-unaveraged). The lag residual's guard, which no table records, is held at or above 32 ulps a substep and measured at 8.8e5.

The ledger row is the mode's own term and not a coordinate, and it is scaled by the energy the step moved rather than by the energy it netted. Over a record step the gains and the losses very nearly cancel, so the net is a small difference of large exchanges. Against it the ratio reaches 3, which is a statement about the cancellation and not about single precision. The turnover is what the ledger's own conservation check normalizes by for the same reason, and what the averaged instrument's phasor row does when it scales to charge rather than to a noise-level sum.

The field row is this mode's and not the averaged instrument's. The mode diffracts once a substep, sixty times a record step on this input file, where the averaged mode diffracts once. The twin therefore keeps its own single-precision record and advances it every substep: a single-precision transform pair against a rounded propagator, then the step's source added. Sixty of those stand behind one row, and the row is read against the FP64 field's norm. The twin's particles gather from the FP64 record throughout, so the eight rows above measure the particle path alone, which is where every reformulation lives, and the field row measures the field arithmetic alone. `fp32_check = "freerun"` is refused for the mode, since freerun compounds a single-precision state across steps and this twin carries none.

## The coarse-step measurement

The manual summarizes this in [](fel-physics.md#sec-numerics).

SIMPLEX's reference case integrates twelve undulator periods per step with the slice spacing matched so slippage is one slice per step -- an order of magnitude fewer steps than one-step-per-period. Whether that economy transfers to this integrator is measured by `run_delz_sweep.sh`. Genesis4 generates one time-dependent initial state (32 slices of spacing `12*lambda0`, shot noise on). The tracker runs the full line from that same dump at `ds_step` of 1, 2, 3, 6 and 12 periods (two-line wrapper lattices overriding `ds_step`), so every run shares one shot-noise realization and the differences are pure integration error. That sharing is what the measurement rests on, and it holds whichever realization the reference produces. The numbers below stand as measured against a Genesis4 predating the 4.6.15 seeding change. A rerun on the current reference draws a different realization and would move them in their own right, which is a property of the comparison rather than of the integrator. Total power at the twelve undulator-segment exits, against the one-period run:

| `ds_step` | max over exits | at saturation |
|---|---|---|
| 2 periods | 1.3e-1 | 1.5e-2 |
| 3 periods | 2.5e-1 | 2.8e-2 |
| 6 periods | 5.1e-1 | 2.1e-2 |
| 12 periods | 7.0e-1 | 2.6e-1 |

The max-over-exits error lives in the exponential-gain region, where a step-size error is a quasi-systematic gain-length shift. Fitted there, convergence is roughly first order (pairwise p of 1.7, 1.1, 0.5). The saturation error is oscillatory (post-saturation power oscillates, so a small phase shift moves the sampled value) and fits no clean order.

Saturation power holds to ~3% up to six periods per step, and the twelve-period matched configuration misses it by 26%. SIMPLEX's step-size economy is tied to its semianalytic field advance and does not transfer to this Genesis4-style integrator as is. `ds_step` of two to three periods is the operating point here. Six periods is defensible when only saturation power matters.

## The interlude's own steps

Tao's comb carries two halves. `save_a_bunch_step` selects among the positions a tracker already reaches, and `tao_lattice_calc_mod`'s beam-track loop cuts an element into `max(1, int(1.01 L / ds))` pieces with `element_slice_iterator` where the tracker would otherwise cross it in one map. `comb_ds_save` here was the first half alone. An FEL element reaches one position per `ds_step`, so the comb had a fine grid to select from inside a wiggler. An interlude was one `track1_bunch` call over the whole element, so it reached one position, its end, and no comb setting added another. A frame series therefore had particles through a wiggler and a single frame through a break. `run.interlude_ds_step` is the second half.

Each piece tracks the beam through its own sliced element, drifts the field by its own length, advances the common phase at the reference rate over it and takes its share of the element's slippage. Slippage is an accumulator in whole slices, so the pieces sum to the element's own and the ring rotates where the light actually passes a slice rather than at the element's end. A chicane's chord-versus-arc correction is a property of the whole break and lands on its last element, so it lands on that element's last piece and the pieces sum to what the element did before.

What the pieces must not do is change the answer. On a wiggler, quadrupole, pipe, wiggler line the exit power and the exit `sigma_x` of a cut run agree with the whole-element run at the levels in [](#val-levels-diagnostics). The pieces come from Bmad's own `element_slice_iterator` rather than from splitting the lattice by hand, which is why an element's fringes stay at its own ends instead of appearing at every cut. What that construction buys is below notice at FEL beam sizes. A hand-split lattice of ten sub-quadrupoles with `fringe_type = full` agrees with the whole element at the same level on the same line, the fringe kick being cubic in a transverse offset of order ten microns. The iterator is the correct construction, and the difference does not show at these beam sizes.

Off is the default and off is the path every run took before the setting existed. An input file naming `interlude_ds_step = 0` reproduces an input file that never names it byte for byte in the diag stream and on every array of the statistics file but the input echo and the timestamp. That is what lets the recorded tier digits stand unmoved. The single-piece branch keeps `z_now = z_now + L` where the several-piece branch takes each boundary from the element's start, so the walk and the setup's record-count precompute reach the same z bit for bit and the stats arrays stay exact-sized.

Two configurations decline the cut, and the shape of both is Tao's. An element carrying a Bmad short-range wake is tracked whole. That wake is a once-per-passage kick of the element's length and pieces would make it one kick a piece, which is the judgment Tao makes where CSR or space charge would see a cut. The chamber wake needs no such refusal, being an energy loss proportional to the length applied additively in gamma, so its pieces sum to the element's own kick. `interlude_model = "genesis"` refuses the setting, that model being a transcription of Genesis's own interlude whose step is the element.

The rows and frames were counted on the checks' own line, a quadrupole of 0.2 m and a pipe of 0.4 m at `interlude_ds_step = 0.04` and `comb_ds_save = 0.02`, and the counts stand in [](#val-levels-diagnostics). The whole element has no row and no frame strictly inside the quadrupole or the pipe, the cut run has several of each with one frame a row under `dump_at_comb`, and the exit power agrees with the whole element.

There is one thing Tao does not do and this program does. Tao's comb gives statistics along an element but its beam dumps stay at element ends, `ix_slice == -1` guarding both the internal save and the dump file. `dump_at_comb` writes a frame at every comb row, so with the pieces on a frame lands wherever a row does, which is what a movie through a break wants.

## The saturation demo

The practical end-to-end case is Genesis4's own Benchmark1-SASE configuration run to saturation over the full 57 m Aramis line, dark start, 96 slices, tracked three ways from identical dumps against one external clock. Its inputs, its run script and its measured result live with the demo itself, in [`../examples/saturation_demo/README.md`](../examples/saturation_demo/README.md). The averaged mode matches Genesis4 at 4.9e-4 through saturation, and the unaveraged mode rides +0.6 ln on the shot-noise radiation channel it physically resolves. On that configuration and machine (M3 Max, 12 performance cores, production builds on both sides) it also ran 1.26x faster at equal cores. That is one case on one machine and *not* a general claim about either code.

Properties of Genesis4 that this transcription had to establish by reading its source are recorded in [](genesis4.md), which is the one page that tracks Genesis4 as it changes.
